# 版本发布与更新流程

> **面向对象**：接手这个项目的人，或任何一个拉取本仓库后要发版的 agent。
> 读完这一篇应该能独立完成一次完整发版，不需要再问任何人。
>
> **最后核对**：2026-09-21（对应版本 `v0.25.0`）
> 本文里的路径、命令、结论都是**当时实测过的**，不是推断。改了发布方式请回来更新这一篇。

---

## 0. 三十秒版（一次发版要做什么）

```bash
# ① 改代码 + 自测（改了 app/ 就必须重建 dist/）
node build.js
npm start

# ② 改版本号 —— 两处三地，见 §2
#    package.json / README.md「当前版本」/ README.md「变更记录」

# ③ 打包并验证
npm run dist
npm run pack          # 出免安装目录，用冒烟脚本快速验

# ④ 提交 + 打 tag（tag 必须单独 push）
git add -A
git commit -m "feat: xxx（0.22.0 → 0.23.0）"
git push origin main
git tag -a v0.23.0 -m "一句话说明这个版本做了什么"
git push origin v0.23.0

# ⑤ 建 Release 并上传安装包 —— 见 §5
```

---

## 1. 先把三个概念分开

这三件事经常被混在一起说，但它们是不同的事、不同的操作：

| 说法 | 实际是什么 | 关键动作 |
|---|---|---|
| **更新代码** | 改代码 → 改版本号 → 自测 | `node build.js`、`npm start` |
| **上传新版本（发布）** | 提交 → 打 tag → 建 Release → 传安装包 | `git push`、`git push origin vX.Y.Z`、建 Release |
| **下载并更新（使用者）** | 装上新版安装包 | 双击新安装包覆盖安装，见 §6 |

---

## 2. 版本号：改一处不够，要动两处三地

沿用 README 既有的语义化版本约定：

- **MAJOR**：不兼容变更（接口破坏、数据格式变化、架构升级）
- **MINOR**：向后兼容的新增能力（新模块、新接口、新配置项）
- **PATCH**：缺陷修复与文档更新

一次改版本号必须同步这**两处文件、三个地方**：

| # | 位置 | 为什么不能漏 |
|---|---|---|
| 1 | `package.json` 的 `"version"` | **唯一真正生效的版本号**。安装包文件名、`latest.yml` 全从它来 |
| 2 | `README.md` 的「当前版本」 | 人看的入口 |
| 3 | `README.md` 的「变更记录」 | 新增一段 `#### x.y.z — 日期`，写清改了什么、为什么 |

> ⚠️ **只改 README 不改 `package.json`**：安装包会顶着旧版本号发出去，`latest.yml` 也是旧的。以后做自动更新时会直接踩坑（更新器认为"没有新版本"）。

## 3. 发布前自测清单

| 步骤 | 命令 | 验证什么 |
|---|---|---|
| 网页版重建 | `node build.js` | 脚本自带校验（`$$` 是否被吞、script/style 块数量、有无残留外部引用），任一不通过会报错退出 |
| 网页版手测 | `node server/index.js` → 浏览器开 `http://127.0.0.1:8787/` | 关键流程能跑通 |
| 桌面版手测 | `npm start` | 窗口能开、界面正常、无控制台报错 |
| 桌面版冒烟 | 见下 | 脚本化确认"界面真的画出来了" |

桌面版冒烟自检（打包后也能用，这是它最大的价值）：

```powershell
$env:JC_DESKTOP_SMOKE=1
$env:JC_SMOKE_DELAY=3000
.\release\win-unpacked\JimengConsole.exe
```

它会截图 + 落一份 DOM 快照 + 打印标题 / 视图几何 / 资源加载状态 / 数据目录 / 外部工具路径，然后自己退出。判断标准：日志里出现 `[smoke] OK`，且 `views` 里对应视图的高度**不是 0**（高度 0 = 页面其实是空白的，这种情况历史上真出现过，见 §9）。

## 4. 打包

```bash
npm run dist    # 正式安装包（NSIS）
npm run pack    # 只出免安装目录 release/win-unpacked/（排障、冒烟用，更快）
npm run icons   # 重新生成 build/icon.png 与 icon.ico（改了图标才需要）
```

`npm run dist` 约 30–60 秒，在 `release/` 下产出四个文件：

| 文件 | 作用 | 要不要传 Release |
|---|---|---|
| `JimengConsole-<版本>-x64-Setup.exe` | 安装包本体（约 106 MB） | **必须** |
| `JimengConsole-<版本>-x64-Setup.exe.blockmap` | 增量更新用的块索引 | 建议传（以后做自动更新要用） |
| `latest.yml` | 更新元数据（版本号 + sha512 + 大小） | 建议传（同上） |
| `builder-debug.yml` | 打包调试信息 | 不用传 |

> **`release/` 已在 `.gitignore` 里，绝对不要提交进 git。** 106 MB 的二进制进 git 会让仓库迅速膨胀（git 保存每个历史版本的完整副本），而且每次发版都要重传全量。
>
> `build/`（图标）则**必须入库** —— 它是打包时的输入，不入库会导致别人克隆后 `npm run dist` 直接失败。

## 5. 建 Release 并上传安装包

### ⚠️ 先理解这条约束：本仓库是**私有库**

私有库的 Release 附件**下载需要登录且有仓库权限**。这带来两个后果：

1. 安装包不能通过匿名链接分享 —— 对方必须被加为仓库协作者
2. **应用自身无法匿名读取 Release 信息**（它跑在用户机器上，没有你的 GitHub 凭据）

第 2 条直接决定了"自动更新"能不能做，详见 §6 方案 C。

### 路 A：网页操作（最省事，不用装任何东西）

1. 打开 `https://github.com/ikun1946/jimeng-console/releases/new`
2. `Choose a tag` 选刚推上去的 tag（如 `v0.23.0`）
3. 标题填版本号，说明填变更要点（可以直接抄 README 的变更记录）
4. 把 `release\JimengConsole-0.23.0-x64-Setup.exe` 拖进附件区
5. 建议同时传 `latest.yml` 和 `.blockmap`
6. Publish release

### 路 B：命令行 API（可自动化）

用 `GITHUB_TOKEN` 调 REST API。本仓库已有同风格的脚本 `scripts/push-to-github.sh`（用 `curl` + `Authorization: Bearer`），照着写即可：

1. `POST /repos/{owner}/{repo}/releases` 建 release，拿到 `upload_url`
2. `POST {upload_url}?name=...` 传附件（`Content-Type: application/octet-stream`）

### 路 C：`gh` CLI（装完最省事）

```powershell
winget install --id GitHub.cli
gh release create v0.23.0 "release\JimengConsole-0.23.0-x64-Setup.exe" --title "0.23.0" --notes "变更要点"
```

> 本机目前**没有安装 `gh`**（2026-09-20 核对）。

## 6. 使用者怎么下载和更新

> ⚠️ **本节已按 0.24.0 更新**：**应用内自更新已经实现**（`desktop/updater.js`）——检查 → 下载 →
> 校验 → 静默安装 → 自动重启，入口在设置抽屉的「应用更新」卡片与托盘菜单。下面三个方案保留下来
> 是为了说明"为什么最后选了这个做法"，以及私有库下更新源怎么配。**日常更新不再需要手动下载安装包。**
>
> 唯一要手动的一次是**首次装上带自更新的版本**（0.24.0 起）—— 因为更早的版本还没有这个能力。

### 方案 A：手动覆盖安装 —— 仍可用（0.24.0 前是唯一方式）

拿到新安装包 → 双击 → 装到同一位置 → 完成。

- **不需要先卸载**：NSIS 安装器认 `appId`（`com.ikun1946.jimengconsole`），装到同一位置会自动覆盖升级
- **数据不会丢**：见 §7
- **缺点**：使用者得自己记得去下载

### 方案 B：应用内"检查更新"提示 —— **0.24.0 已实现**（实现形态见下）

比对版本号 → 有新版弹提示 → 用系统浏览器打开下载页。

因为私有库不能匿名读取（§5），版本信息要放在一个**匿名可读的小文件**里（公开 gist / 静态托管），应用读它、比对、然后开浏览器。**下载动作仍走浏览器**，用户在浏览器里是登录状态，能打开私有库的 Release 页。

**关键设计原则：绝不在应用里嵌 GitHub 令牌。** 安装包是可解压的，嵌进去等于公开整个私有仓库的读权限。

### 方案 C：全自动更新（electron-updater）—— 当前**不建议做**

打包侧其实**已经就绪**：`release\latest.yml` 每次打包都会自动生成，正是 electron-updater 要读的文件。

但私有库上走不通，必须二选一：

- 把令牌嵌进应用 → **禁止**（理由同上）
- 把安装包放到匿名可访问的地方（公开仓库的 Release，或自建更新源）→ 可行，但要额外维护一个仓库

另外：没有代码签名时，**首次安装**仍会弹 SmartScreen 警告；`latest.yml` 必须和安装包一起传，否则更新会静默失败。

## 7. 数据安全与回滚

### 为什么升级不会丢数据（三层保护，都已实现）

| 层 | 机制 | 位置 |
|---|---|---|
| 1 | **物理隔离** —— 数据、配置、日志全在安装目录之外，安装器碰不到 | 数据在 `%USERPROFILE%\Videos\JimengConsole\`；配置与日志在 `%APPDATA%\即梦批量生成控制台\` |
| 2 | **迁移前自动备份** —— schema 变化前把旧库完整备份 | `server/store.js` 的 `backupBeforeMigration()` → 数据目录的 `backup\`（**不参与**滚动轮转，不会被挤掉） |
| 3 | **日常滚动备份** —— 每次写盘前把上一版另存 | `db.json.bak-<时间>`，保留最近 12 份（`BACKUP_KEEP`） |

另外 `electron-builder.yml` 里 `deleteAppDataOnUninstall: false`：**卸载只删程序，不删数据**。所以"卸载重装"是很安全的排障手段。

### ⚠️ 真正的风险是"降级"，不是"升级"

新版本如果迁移过数据库（比如 schema v3 → v4），**旧版本的程序可能读不懂新格式**。装回旧版不一定能跑。

回滚的正确做法：

1. **升级前**把 `db.json` 复制一份到别处
2. **保留旧安装包**，别装完就删
3. 万一要回退：卸载新版 → 装回旧版 → 如果读不了库，用升级前的 `db.json` 覆盖回去

## 8. 红线（这些事绝对不要做）

| 不要做 | 原因 |
|---|---|
| 不要提交 `server/data/` | 那是运行数据（含用户的素材与视频），且已在 `.gitignore` 里 |
| 不要提交 `release/` | 上百 MB 的二进制，会把仓库撑爆 |
| 不要删 `build/icon.*` | 打包的输入，删了 `npm run dist` 会失败 |
| 不要在应用里嵌 GitHub 令牌 | 安装包可解压，等于公开私有仓库读权限 |
| 不要删用户的 `db.json` 或 `projects/` | 那是用户的全部数据，且**不可恢复** |
| 不要跳过"真装一次"这一步 | 快捷方式 / 安装路径 / 卸载项的问题只有真装才暴露 |
| 不要只改 README 版本号 | 见 §2 的警告 |
| 不要忘记 `git push origin vX.Y.Z` | 普通 `git push` 不推 tag，回退点会只留在本地 |

## 9. 已知发布阻塞项（**尚未解决**）

对外公开分发前必须处理，别当成已经完成了：

1. **仓库没有 `LICENSE` 文件** —— 公开前要先定授权范围
2. **`dreamina.exe` 未签名，且未确认允许再分发** —— 所以桌面版只做**检测**，不内置
3. **FFmpeg 是 GPL 构建**，且单个二进制约 212 MB —— 同样未内置
4. **安装包没有代码签名**（`Get-AuthenticodeSignature` = `NotSigned`）—— 使用者首次安装会看到 SmartScreen 警告，需要点"仍要运行"

## 10. 一个真实踩过的坑（留作参考）

**症状**：打包后的应用双击打开，窗口出现了但**一片空白**，几秒后才显示首页。

**排查过程**：截图是纯白 → 先怀疑样式没加载，但 `styles.css / api.js / app.js` 全部返回 200；再怀疑 JS 报错，但渲染进程没有任何 error；最后拉出 DOM 快照才发现三层视图（`#homeView` / `#projView` / `#app`）**全都还是 `hidden`** —— 说明 `boot()` 根本没走到"显示某一层"那一步。

**根因**：`app/app.js` 的 `bootFromUrl()` 里 `await loadAdapterOnly()` —— 这次适配器探测要真去问一次 dreamina CLI，**实测 2.5 秒**才返回。在浏览器里这段等待只是白一下，但在桌面窗口里就是"程序坏了"的观感。

**修法**：改成只发起、不等待，结果回来再补一次顶栏。首屏从 >2.5s 降到 1.5s 内可见。

**留下的教训（已固化进工具）**：

- 冒烟脚本现在会打印**视图几何**而不只是"元素是否存在" —— 因为 `querySelector` 在元素存在但 `display:none` 时同样返回 true，"存在"不等于"看得见"
- 渲染进程的 `error` 级控制台消息会一律转进 `logs\main.log` —— 打包版没有 DevTools，页面抛异常的表现就是白屏，这条日志是唯一线索
- 冒烟脚本里保留了故意报错的 `SMOKE-SELFTEST-ERROR` —— 用来确认"日志里没报错"是真的没报错，而不是日志链路本身断了

## 11. 相关文件速查

| 文件 | 管什么 |
|---|---|
| `package.json` | 版本号（唯一生效来源）、依赖、`start` / `pack` / `dist` / `icons` 脚本 |
| `electron-builder.yml` | 安装包配置：appId、文件白名单、NSIS 行为、不删用户数据 |
| `desktop/runtime-paths.js` | 目录布局唯一事实来源（数据根 / 配置 / 日志放哪） |
| `desktop/main.js` | 主进程：单实例、窗口、托盘、旧数据导入入口、优雅退出 |
| `desktop/legacy-import.js` | 旧版 `server/data` → 桌面版数据目录的导入与完整性体检 |
| `scripts/make-icons.js` | 生成 `build/icon.png` 与 `icon.ico` |
| `build.js` | 把 `app/` 内联成 `dist/` 单文件网页版 |
| `.gitignore` | 哪些东西不许入库（`release/`、`server/data/`、`node_modules/`） |

配套文档：`README.md`（项目总览与桌面版说明）、`AGENTS.md`（给 agent 的硬性约定）、`docs/Git 私密仓库操作指南.md`（令牌与私密性）。
