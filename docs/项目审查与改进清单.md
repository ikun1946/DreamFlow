## 二、P0：发布前必须处理

### 1. 修复自更新文件名的路径穿越风险

**涉及文件：** `desktop/updater.js`

当前更新文件名来自 `latest.yml`，并直接拼接到目标路径：

```js
const dest = path.join(destDir, m.file);
const localPath = path.join(source.dir, m.file);
```

如果更新清单中的文件名包含 `../`、绝对路径或路径分隔符，理论上可能逃出预期目录。

**建议：**

- 只允许普通文件名，不允许目录结构。
- 禁止绝对路径、`..`、`/`、`\\` 和 NUL 字符。
- 只允许 `.exe` 文件。
- 最好限制为当前产品的安装包命名格式，例如：

```text
JimengConsole-<version>-x64-Setup.exe
```

可增加统一校验函数：

```js
function safeArtifactName(name) {
  const value = String(name || '');
  if (!value || path.basename(value) !== value) {
    throw new Error('更新文件名非法：' + value);
  }
  if (value.includes('\0') || value.includes('/') || value.includes('\\')) {
    throw new Error('更新文件名不得包含路径分隔符');
  }
  if (!/^[A-Za-z0-9._-]+\.exe$/i.test(value)) {
    throw new Error('更新文件名不是合法的安装包名称');
  }
  return value;
}
```

应在解析 manifest 后、读取本地更新包前、开始下载前分别保证文件名已经通过校验。

### 2. 修复安装器启动状态竞争

**涉及文件：** `desktop/updater.js`

当前 `install()` 在调用 `spawn()` 后立即返回成功，同时又注册了异步 `error` 事件：

```js
child.on('error', (e) => resolve({ ok: false, error: '调起安装器失败：' + e.message }));
child.unref();
resolve({ ok: true });
```

这会导致调用方先收到成功结果；如果随后进程启动失败，错误已经无法正确传递。

**建议：**

- 使用一次性 `finish()` 防止重复 resolve。
- 在成功创建子进程后再返回成功。
- 监听 `error`，并在失败时保留当前应用，不要立即退出。
- 安装前再次确认目标文件存在且已经通过 SHA-512 校验。

### 3. 增加更新流程互斥锁

**涉及文件：** `desktop/main.js`、`desktop/updater.js`

更新既可以从设置页触发，也可以从托盘菜单触发。需要防止重复检查、重复下载和重复安装。

**建议：**

- 增加 `updateBusy` 或状态机：`idle / checking / downloading / ready / installing`。
- 检查、下载、安装期间禁止重复调用。
- 下载失败时清理 `.part-*` 临时文件。
- 应用启动时清理过期临时文件。
- 同一版本重复下载时使用安全的临时路径，校验通过后再原子重命名。
- 安装期间禁用退出流程中的冲突操作。

### 4. 补充 LICENSE 和第三方声明

当前仓库没有正式 `LICENSE`，README 已将其列为发布阻塞项。

需要明确：

- 项目本身采用什么许可证，或者明确暂不授权复制和分发。
- `dreamina` CLI 不随安装包分发的原因和边界。
- FFmpeg 的许可证与分发方式。
- 图标、字体及其他外部资源的授权来源。
- 第三方软件的许可证不能自动继承项目自身的许可证。

### 5. 完成 Windows 安装包签名方案

当前安装包没有代码签名，用户可能看到 SmartScreen 警告。

正式发布前建议：

- 准备 Windows 代码签名证书。
- 使用 `CSC_LINK` 和 `CSC_KEY_PASSWORD` 配置签名。
- 证书不得提交到仓库。
- 在 CI 或安全的本地环境中保存签名凭据。
- 同时验证安装器和主程序的签名。
- 在干净 Windows 环境完成安装、升级和卸载测试。

当前项目当时缺少测试兜底，但项目复杂度已经不适合完全依赖手工验证。

- 项目隔离。
- 工作区父子关系校验。
- 路径穿越防护。

- 活动任务期间禁止删除。

- schema 迁移和迁移失败回滚。

#### 任务逻辑

#### 构建与发布

- `node build.js`。
- 版本号一致性。
- Electron 打包。
- 更新清单解析。
- SHA-512 校验。
- 更新文件名安全校验。

不必一次性恢复所有历史测试，先恢复 10–20 个关键测试也有明显收益。

## 四、P1：外部工具和用户环境

### 10. 统一外部工具缺失时的行为

项目依赖：

- `dreamina`
- `ffmpeg`
- `ffprobe`

建议固定以下等级：

| 工具 | 缺失影响 | 应用行为 |
|---|---|---|
| dreamina | 无法生成视频 | 阻止提交，显示安装/登录入口 |
| ffmpeg | 无法生成封面 | 允许生成，但明确提示封面缺失 |
| ffprobe | 无法读取音频时长 | 禁止绑定无法确认时长的音频 |

建议为这些状态建立稳定错误码，而不是只依赖自由文本：

```text
CLI_NOT_FOUND
FFMPEG_NOT_FOUND
FFPROBE_NOT_FOUND
CLI_NOT_LOGGED_IN
CLI_PERMISSION_DENIED
```

每个错误码都应同时有：

- 后端错误响应。
- 前端用户提示。
- 日志文本。
- 可执行的解决动作。

### 11. 检查首次启动的旧数据导入流程

**涉及文件：** `desktop/main.js`

当前用户选择“以后再说”后，会写入 `legacyImportChecked: true`，后续启动不再自动询问，只能从托盘菜单手动导入。

如果这是设计目标，建议把按钮文案明确为：

```text
以后再说（可从托盘菜单重新导入）
```

如果希望下次继续询问，则不要在选择“以后再说”时永久写入完成标记。

同时建议增加：

- 导入前目标目录备份。
- 导入后的数据库结构校验。
- 导入失败后的目标目录恢复。
- 导入报告保存到日志或数据目录。

## 五、P2：数据可靠性和可恢复性

### 12. 增强 JSON 数据库损坏恢复

建议启动时采用以下恢复策略：

```text
读取 db.json
  ├─ 成功且结构合法 → 正常启动
  ├─ JSON 损坏 → 尝试最新备份
  ├─ 最新备份损坏 → 逐个尝试旧备份
  └─ 全部失败 → 安全启动为空库，但必须明确提示用户
```

不能把 JSON 解析失败静默当成空库，否则用户会误以为项目被删除。

建议检查：

- 写临时文件后是否尽可能 `fsync`。
- rename 前后中断是否可恢复。
- 启动时是否自动检测 `db.json` 损坏。
- 备份是否有数量上限。
- 使用备份恢复时是否写入日志。
- 数据迁移失败时原文件是否保持不变。

### 13. 完善彻底删除的二次保护

彻底删除会移除项目、分镜表、分镜、素材、生成记录以及磁盘文件，属于不可逆操作。

建议删除前显示：

- 项目名称和 ID。
- 分镜表数量。
- 分镜数量。
- 素材数量。
- 视频和封面文件数量。
- 大致磁盘占用。

建议删除流程增加：

- 删除前自动创建一次不可覆盖备份。
- 删除完成后检查项目目录确实不存在。
- 失败时报告已删除和未删除的文件。
- 记录项目 ID、名称、时间和文件数量。
