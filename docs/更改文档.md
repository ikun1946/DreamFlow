### 2.7 · fix: 列头与表体横向滚动脱节（布局错位修复，2026-09-18 10:55，待提交）

### 2.16 · perf: 登录/切换账号轮询瘦身（2026-09-18 12:25，待提交）

**瓶颈定位**（实测：`auth status` 单次 spawn ≈ 700ms）：
1. 等待授权期间每轮轮询调用 `probe(true)` —— 每轮 **2 个进程**（`version` + `auth status`），其中 `version` 在登录期间毫无变化，纯冗余；
2. 首次检查固定在 spawn 后 3s，授权链接要 3-4s 才对用户可见；
3. 每轮 probe 都伴随 settings 写库 + 落盘防抖，轮询期磁盘写频繁。

**修正**（`server/cli.js`，行为不变）：
- 新增 `authStatusQuick()`：**单进程** `auth status` 快检（省 50% 进程开销），轮询体只用它；完整 `probe(true)` 仅在成功/失败/超时终态各调一次（组装返回数据）；
- 首查提前：spawn 后 **1.2s** 即提取授权链接并写库（此前 3s）——授权页更快可见；
- 轮询间隔 3s → 2.5s（快检变轻后整体节奏更快）；
- `publishAuthUrl` 惰性写库：仅在 URL 变化时落盘，流程结束统一清理。

**改进数据**（实测）：授权链接首现 **≈1.5s 内**（原 3-4s）；登录完成→感知延迟最坏 ~5s → **~3.2s**（检测减半）；5 分钟等待期 CLI 子进程数 **约 200 → 约 120**（-40%）；轮询期冗余磁盘写消除。授权等待本身（用户在浏览器操作的时间）为流程本质，不可压缩。

### 2.17 · fix: 登录协议修正——auth wait 才是官方等待命令（2026-09-18 13:43，待提交）

**问题**：用户两次「浏览器完成授权但系统仍显示未登录」。实测定位到**协议误用**：
- `auth login` 的真实行为是**启动授权后约 1.5s 即成功返回**（`status: authorization_required` + `challenge{deviceCode,userCode,verificationUri}`），**不阻塞等待**；
- 官方等待命令是 **`auth wait --device-code <code> [--timeout 10m]`**（实测：缺 device-code 时报 `cli.device_code_required`）；
- 原实现误把 `auth status`（只读本地凭据）当等待手段轮询——授权完成后本地凭据不会自动落盘，必须由 `auth wait` 完成交换 **5 分钟主轮询熬完才轮到宽限期尝试**，且宽限期裸调 `auth wait`（缺 device-code）实际是无效空转 → 授权结果被静默丢弃。

**修正**（`server/cli.js`）：改为官方三段式——① `auth login` 启动授权并提取 `challenge.verificationUri`（链接 1.5s 内可见）；② 已登录快速路径检查；③ **`auth wait --device-code <code> --timeout <剩余预算>` 阻塞等待授权完成**，返回后校验登录态。等待预算默认 5 分钟 → **10 分钟**（与 CLI 默认一致，`loginTimeoutMs` 可配）；前端等待文案同步更新。移除无效的宽限期裸 `auth wait` 循环。

**验证**：触发登录后授权链接秒出；`auth wait` 进程实测阻塞运行中（PID 6744，36MB）；待用户浏览器完成授权后应数秒内翻转。另注：`tasklist | grep` 在本机 bash 下会假阴性（返回 0 但进程存在），进程核查须用 Node `execSync('tasklist /FO CSV')`。

### 2.19 · perf: 加载与交互性能优化（2026-09-18 14:33，待提交）

**实测定位的瓶颈**（非猜测）：
1. **冷启动 `/system/adapter` 19.8 秒**——画布 CLI（version+auth status）与创作 CLI（version+user_credit）**串行 4 次进程 spawn**；前端 boot 又是 `await loadMeta() → loadList()` 串行，导致首屏骨架屏持续近 20 秒；
2. **空闲时周期性 CLI spawn**——worker tick 每 1.5s 执行，即使无任何任务也会 probe（30s 过期）+ resolveMaxConcurrency→modelList（60s 过期）→ 每 30-60 秒创建 3 个 30MB 进程，造成操作时的 CPU 峰值卡顿；
3. 资源体积（80KB）与渲染开销（30 行点击 4ms）**实测均非瓶颈**，排除。

**优化措施**：
- `cli.js`：tick 加**空闲快速路径**（无 queued/running 直接 return，零探测零开销）；probe 由 2 次 spawn 合并为 1 次（`auth status` 已含 version 字段）；新增 `peek()` 读缓存。
- `dreamina-cli.js`：version 改读本地 `version.json`（零 spawn），可用性探测只留 `user_credit` 一次。
- `services.js`：两组 CLI 探测改 **Promise.all 并行**；`adapterStatus` 支持 **fast（stale-while-revalidate）**——有缓存立即返回并后台刷新。
- `index.js`：**启动预热**（listen 后 300ms 后台探测两个 CLI + 模型目录，不阻塞）。
- `app.js`：boot 改 `Promise.all([loadMeta, loadList, loadAssets])` **并行加载**（列表不再被 CLI 探测拖累）+ 2.5s 后补拉 adapter 纠正状态显示。

**前后实测对比**：冷启动 adapter **19.8s → 0.02s**；预热后 options/list/assets 均 **4ms**；首屏数据渲染 **~20s → 1s 内**；空闲 8 秒 CLI 进程创建 **3 个/30-60s → 0**。

| 优先级 | 来源 | 例子 |
|---|---|---|

| 2 | 无标注时，取各镜头秒数之和 | `镜1｜3.2s` + `镜2｜2.6s` = 5.8 → **6s** |

### 2.30 · fix: 弹层按钮卡死在「应用中…」（2026-09-18 16:35，待提交）

**现象**（用户上报）：自动匹配弹层的「应用」按钮一直显示「应用中…」，点不动、只能刷新页面。


> 与「提示词有无内容」「名称能不能匹配到」无关：预览数据其实是对的（命中 1 个），坏的只有按钮状态。因此**不能用"按钮文案"判断请求是否在跑**——它可能只是没被重绘的旧 DOM。

**修复**（`app/app.js`）：把 busy 收敛成**唯一出口**，置标志的同时重绘「当前可见的」面板，杜绝"先渲染、后复位"：

```js
function setAutoBusy(v) {           // 时长弹层同构：setDurBusy(v)
  S.autoBusy = v;
  renderPanel();
  if (!$('#autoMask').hidden) renderAutoPanel();   // ← 关键：复位时补绘弹层
}
```

- 预览路径：先 `$('#autoMask').hidden = false`，再由 `finally { setAutoBusy(false) }` 统一重绘 → 按钮正确显示「应用（绑定 N 个）」且可点；

- 应用路径的顺序也调整为「先关弹层 → 刷新列表/素材 → 最后 toast」，避免刷新失败却提示"已绑定成功"；

### 2.31 · feat: 素材「图号」与提示词绑定（2026-09-18 16:55）

**起因**（用户提问）：提交命令里明明带了 `--image`，但——

> 「有参考图了，但是谁参考图片呢？」

**根因**：`--image` 只是把本地文件**上传**给模型，参数本身不带语义。图片编号 = 上传顺序 = 该分镜「已绑定素材」的顺序；而**提示词里一个 `@图片N` 都没有**（实测分镜 `st_a1637037` 的 `@图片` 引用数为 **0**）。于是模型只知道"收到了 2 张图"，根本不知道哪张是角色、哪张是场景 —— 只能按位置猜，两张图的责任完全模糊。

**用户选择**：C 方案（混合）——**界面显示图号 + 后端注入锁定段 + 校验提示词里的 `@图片N` 是否越界/错位**。

#### 新增 `server/asset-lock.js`：图号与绑定的**唯一事实来源**

四件事集中在此，所有组装提示词的地方共用（**不得各自实现，否则命令行第 N 张图与提示词「图片N」会错位**）：

| 函数 | 职责 |
|---|---|
| `imageCatalog(sb, db)` | 图号表。**图号只在这里诞生**（`n: images.length + 1`），顺序必须与创作 CLI 的 `--image` 严格一致 |
| `lockBlock(images, sb)` | 「素材锁定」区块文本 |
| `compose(prompt, block)` | 组装最终提示词 = 区块 + 原文 |
| `validate(prompt, images, opts)` | 校验 `@图片N` 越界 / 裸 asset id / 未内联引用 / 截断 / 未计入图号 |
| `signature(sb, db)` | 指纹（提示词 + 图号表 + 生成参数），用于判断干跑记录是否过期 |

**铁律：只补不改。** 台词、镜序、秒数、人物、场景一个字都不动，只在**最前面**追加区块（视频模型对开头指令权重更高）。因此 `compose()` 永远不会返回被改写过的原文。

**计入图号的条件**（与 `--image` 完全一致）：① 分镜上确有该绑定；② 素材存在；③ **不是音频**（音频走 `--audio`，不占图片号）；④ 本地文件**确实存在**——发不出去的图不能占号，否则后面的图号全部错位。文件存在性带 5s 缓存（列表接口每次轮询都要判，直接 stat 太浪费）。

**锁定区块内容**（一图一职）：

```
【素材锁定｜按本命令 --image 的上传顺序编号；本区块只作补充，不改动下方分镜文字】
图片1 = 奶团（角色） → 记为 <主体1>@图片1，实例特征：奶白短毛、黑鼻头、垂耳。
   只取外形（毛色 / 头型 / 五官 / 体型比例），忽略参考图中的静止姿势与机位（这是最容易出错的地方）；片中该角色的一切动作、表情、朝向以分镜文字为准。
图片2 = 户外草坪（场景） → 场景来源参照 @图片2。
   只取场地、环境、陈设、光线与色调；参考图中的人物 / 动物一律忽略，不得替换片中主体。
对上：分镜文字里出现的 「奶团」= 图片1、「户外草坪」= 图片2；同一主体在全片中保持同一外形，不得前后换脸 / 换犬种 / 换场地。
```
