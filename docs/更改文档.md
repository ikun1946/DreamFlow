**实测**（当前未开通账号）：`meta/options` 下发 `concurrency: {min:1, max:2, defaultValue:2}`（basic 档）；`PUT concurrency=5` → `40001「范围为 1–2（当前账号并发上限 2）」`；合法值 `2` 写入成功。premium/CLI 显式字段路径在账号开通后自动生效（无法在当前账号实测，逻辑已覆盖）。

### 2.16 · perf: 登录/切换账号轮询瘦身（2026-09-18 12:25，待提交）

**瓶颈定位**（实测：`auth status` 单次 spawn ≈ 700ms）：
1. 等待授权期间每轮轮询调用 `probe(true)` —— 每轮 **2 个进程**（`version` + `auth status`），其中 `version` 在登录期间毫无变化，纯冗余；
2. 首次检查固定在 spawn 后 3s，授权链接要 3-4s 才对用户可见；
3. 每轮 probe 都伴随 settings 写库 + 落盘防抖，轮询期磁盘写频繁。

**修正**（`server/cli.js`，行为不变）：
- 新增 `authStatusQuick()`：**单进程** `auth status` 快检（省 50% 进程开销），轮询体只用它；完整 `probe(true)` 仅在成功/失败/超时终态各调一次（组装返回数据）；
- 首查提前：spawn 后 **1.2s** 即提取授权链接并写库（此前 3s）——授权页更快可见；
- 轮询间隔 3s → 2.5s（快检变轻后整体节奏更快）；
- `publishAuthUrl` 惰性写库：仅在 URL 变化时落盘，流程结束统一清理。

**改进数据**（实测）：授权链接首现 **≈1.5s 内**（原 3-4s）；登录完成→感知延迟最坏 ~5s → **~3.2s**（检测减半）；5 分钟等待期 CLI 子进程数 **约 200 → 约 120**（-40%）；轮询期冗余磁盘写消除。授权等待本身（用户在浏览器操作的时间）为流程本质，不可压缩。

### 2.17 · fix: 登录协议修正——auth wait 才是官方等待命令（2026-09-18 13:43，待提交）

**问题**：用户两次「浏览器完成授权但系统仍显示未登录」。实测定位到**协议误用**：
- `auth login` 的真实行为是**启动授权后约 1.5s 即成功返回**（`status: authorization_required` + `challenge{deviceCode,userCode,verificationUri}`），**不阻塞等待**；
- 官方等待命令是 **`auth wait --device-code <code> [--timeout 10m]`**（实测：缺 device-code 时报 `cli.device_code_required`）；
- 原实现误把 `auth status`（只读本地凭据）当等待手段轮询——授权完成后本地凭据不会自动落盘，必须由 `auth wait` 完成交换 **5 分钟主轮询熬完才轮到宽限期尝试**，且宽限期裸调 `auth wait`（缺 device-code）实际是无效空转 → 授权结果被静默丢弃。

**修正**（`server/cli.js`）：改为官方三段式——① `auth login` 启动授权并提取 `challenge.verificationUri`（链接 1.5s 内可见）；② 已登录快速路径检查；③ **`auth wait --device-code <code> --timeout <剩余预算>` 阻塞等待授权完成**，返回后校验登录态。等待预算默认 5 分钟 → **10 分钟**（与 CLI 默认一致，`loginTimeoutMs` 可配）；前端等待文案同步更新。移除无效的宽限期裸 `auth wait` 循环。

**验证**：触发登录后授权链接秒出；`auth wait` 进程实测阻塞运行中（PID 6744，36MB）；待用户浏览器完成授权后应数秒内翻转。另注：`tasklist | grep` 在本机 bash 下会假阴性（返回 0 但进程存在），进程核查须用 Node `execSync('tasklist /FO CSV')`。

### 2.19 · perf: 加载与交互性能优化（2026-09-18 14:33，待提交）

**实测定位的瓶颈**（非猜测）：
1. **冷启动 `/system/adapter` 19.8 秒**——画布 CLI（version+auth status）与创作 CLI（version+user_credit）**串行 4 次进程 spawn**；前端 boot 又是 `await loadMeta() → loadList()` 串行，导致首屏骨架屏持续近 20 秒；
2. **空闲时周期性 CLI spawn**——worker tick 每 1.5s 执行，即使无任何任务也会 probe（30s 过期）+ resolveMaxConcurrency→modelList（60s 过期）→ 每 30-60 秒创建 3 个 30MB 进程，造成操作时的 CPU 峰值卡顿；
3. 资源体积（80KB）与渲染开销（30 行点击 4ms）**实测均非瓶颈**，排除。

**优化措施**：
- `cli.js`：tick 加**空闲快速路径**（无 queued/running 直接 return，零探测零开销）；probe 由 2 次 spawn 合并为 1 次（`auth status` 已含 version 字段）；新增 `peek()` 读缓存。
- `dreamina-cli.js`：version 改读本地 `version.json`（零 spawn），可用性探测只留 `user_credit` 一次。
- `services.js`：两组 CLI 探测改 **Promise.all 并行**；`adapterStatus` 支持 **fast（stale-while-revalidate）**——有缓存立即返回并后台刷新。
- `index.js`：**启动预热**（listen 后 300ms 后台探测两个 CLI + 模型目录，不阻塞）。
- `app.js`：boot 改 `Promise.all([loadMeta, loadList, loadAssets])` **并行加载**（列表不再被 CLI 探测拖累）+ 2.5s 后补拉 adapter 纠正状态显示。

**前后实测对比**：冷启动 adapter **19.8s → 0.02s**；预热后 options/list/assets 均 **4ms**；首屏数据渲染 **~20s → 1s 内**；空闲 8 秒 CLI 进程创建 **3 个/30-60s → 0**。

### 2.28 · feat: 分镜时长按提示词「总时长」标注自动计算（2026-09-18 16:20，待提交）

**需求**：每条分镜的时长由输入提示词里指定的总时长自动算出；**出现小数一律向上进位**；各分镜分配合理且总和与总时长一致。

**取值规则**（`server/services.js` 的 `parsePromptDuration`）：

| 优先级 | 来源 | 例子 |
|---|---|---|
| 1 | 提示词里的 `总时长：X.Xs` 标注 | `段落2｜总时长：4.3s` → **5s** |
| 2 | 无标注时，取各镜头秒数之和 | `镜1｜3.2s` + `镜2｜2.6s` = 5.8 → **6s** |
| — | 两者都没有 | 保持原值，并在预览里标「提示词无时长信息」 |

- **进位一律 `Math.ceil`**：`4.0→4`、`4.3→5`、`5.05→6`。理由：分镜时长必须**装得下**整段内容，宁可多 1 秒；
- **超出全局范围（4–15s）按边界钳制**并提示（如标注 16.5s → 进位 17 → 钳到 15）；
- **标注与镜头之和不一致**（`|标注 − 镜头和| > 0.05`）时以**标注为准**，并在弹层与导入预览里告警，提示回去核对分镜稿；
- 已完成 / 生成中的分镜时长已锁定，跳过不动。

**「总和与总时长一致」如何保证**：进位只在**单条**级别发生一次，不存在跨段累积漂移。接口在 `stats` 里给出可核验的三栏：
`declaredSum`（标注总时长）→ `declaredCeilSum`（各段分别进位后的合计）→ `sumAfter`（实际设定合计），
`consistent = (sumAfter === declaredCeilSum)`。当存在钳制 / 无标注 / 已锁定的分镜时 `consistent` 为 false，并逐项列出原因。
注：因逐条进位，`sumAfter` 会**略大于** `declaredSum`（如 12.3s 分三段 4.1 → 15s），这是刻意设计，不是误差。

**三处生效点**：
1. **导入即生效**——`importConfirm` 创建分镜时用标注值覆盖默认时长；`importPreview` 在预览里直接显示每段「将采用 X s」并对矛盾/越界给出 `DURATION_MISMATCH` / `DURATION_CLAMPED` 警告；
2. **批量重算**——`POST /storyboards/auto-duration`（路由 30 条），`apply:false` 只预览；
3. **手动改坏可纠正**——重算会把任何偏离标注值的时长改回标注值（实测 15s → 5s）。

**页面**：状态栏新增「按时长标注重算」（不勾选 = 全部「未提交」分镜，勾选 = 仅所选）→ 预览弹层（三栏合计 + 逐条「当前 → 目标」与依据）→ 「应用」。

**实测**（6 条样本，跑完已清理）：标注 4.0→4、4.3→5、5.05→6、无标注 5.8→6、无时长信息保持 12、16.5→钳 15；导入落库即正确；改坏后重算纠正；幂等复跑 0 改动。

### 2.30 · fix: 弹层按钮卡死在「应用中…」（2026-09-18 16:35，待提交）

**现象**（用户上报）：自动匹配弹层的「应用」按钮一直显示「应用中…」，点不动、只能刷新页面。

**浏览器实测复现**（agent-browser，与用户截图逐字一致）：

```
弹层已打开: true
标题:      "自动匹配参考图 · 将绑定 1 个"
统计:      "扫描 1 条 · 命中 1 · 已存在 0 · 类型已占 0 · 无匹配 0"
```

> 与「提示词有无内容」「名称能不能匹配到」无关：预览数据其实是对的（命中 1 个），坏的只有按钮状态。因此**不能用"按钮文案"判断请求是否在跑**——它可能只是没被重绘的旧 DOM。

**同类缺陷**：上一轮新增的「按时长标注重算」弹层（`openDurRecalc` / `renderDurPanel`）写法完全相同 —— 同样会在预览后卡死为禁用的「应用中…」。一并修复。

```js
function setAutoBusy(v) {           // 时长弹层同构：setDurBusy(v)
  S.autoBusy = v;
  renderPanel();
  if (!$('#autoMask').hidden) renderAutoPanel();   // ← 关键：复位时补绘弹层
}
```

- 预览路径：先 `$('#autoMask').hidden = false`，再由 `finally { setAutoBusy(false) }` 统一重绘 → 按钮正确显示「应用（绑定 N 个）」且可点；
- 应用路径：`finally` 同样走 `setAutoBusy(false)` → **请求失败时按钮自动恢复可点**，不再需要刷新页面；
- 应用路径的顺序也调整为「先关弹层 → 刷新列表/素材 → 最后 toast」，避免刷新失败却提示"已绑定成功"；
- 「覆盖同类型已有绑定」勾选若发生在预览请求进行中，改为记 `S.autoPending` 并在忙完后自动补跑一次（否则界面仍是旧结果，容易误判）。

**修复后实测**（同一浏览器）：预览后按钮 = 「应用（绑定 1 个）」且 `disabled = false`；点「应用」→ 弹层关闭、服务端落库 `character: 奶团`；时长弹层显示「无需修改」（0 条需改）而非「应用中…」。

**教训**：手动维护 `busy` 标志时，"渲染"与"复位"必须成对且顺序正确；凡按标志决定 UI 文案/禁用态的面板，复位后都必须重绘一次。**别用按钮文案判断请求是否在跑**。

### 2.31 · feat: 素材「图号」与提示词绑定（2026-09-18 16:55）

**起因**（用户提问）：提交命令里明明带了 `--image`，但——

> 「有参考图了，但是谁参考图片呢？」

**根因**：`--image` 只是把本地文件**上传**给模型，参数本身不带语义。图片编号 = 上传顺序 = 该分镜「已绑定素材」的顺序；而**提示词里一个 `@图片N` 都没有**（实测分镜 `st_a1637037` 的 `@图片` 引用数为 **0**）。于是模型只知道"收到了 2 张图"，根本不知道哪张是角色、哪张是场景 —— 只能按位置猜，两张图的责任完全模糊。

**用户选择**：C 方案（混合）——**界面显示图号 + 后端注入锁定段 + 校验提示词里的 `@图片N` 是否越界/错位**。

#### 新增 `server/asset-lock.js`：图号与绑定的**唯一事实来源**

四件事集中在此，所有组装提示词的地方共用（**不得各自实现，否则命令行第 N 张图与提示词「图片N」会错位**）：

| 函数 | 职责 |
|---|---|
| `imageCatalog(sb, db)` | 图号表。**图号只在这里诞生**（`n: images.length + 1`），顺序必须与创作 CLI 的 `--image` 严格一致 |
| `lockBlock(images, sb)` | 「素材锁定」区块文本 |
| `compose(prompt, block)` | 组装最终提示词 = 区块 + 原文 |
| `validate(prompt, images, opts)` | 校验 `@图片N` 越界 / 裸 asset id / 未内联引用 / 截断 / 未计入图号 |
| `signature(sb, db)` | 指纹（提示词 + 图号表 + 生成参数），用于判断干跑记录是否过期 |

**铁律：只补不改。** 台词、镜序、秒数、人物、场景一个字都不动，只在**最前面**追加区块（视频模型对开头指令权重更高）。因此 `compose()` 永远不会返回被改写过的原文。

**计入图号的条件**（与 `--image` 完全一致）：① 分镜上确有该绑定；② 素材存在；③ **不是音频**（音频走 `--audio`，不占图片号）；④ 本地文件**确实存在**——发不出去的图不能占号，否则后面的图号全部错位。文件存在性带 5s 缓存（列表接口每次轮询都要判，直接 stat 太浪费）。

**锁定区块内容**（一图一职）：

```
【素材锁定｜按本命令 --image 的上传顺序编号；本区块只作补充，不改动下方分镜文字】
图片1 = 奶团（角色） → 记为 <主体1>@图片1，实例特征：奶白短毛、黑鼻头、垂耳。
   只取外形（毛色 / 头型 / 五官 / 体型比例），忽略参考图中的静止姿势与机位（这是最容易出错的地方）；片中该角色的一切动作、表情、朝向以分镜文字为准。
图片2 = 户外草坪（场景） → 场景来源参照 @图片2。
   只取场地、环境、陈设、光线与色调；参考图中的人物 / 动物一律忽略，不得替换片中主体。
对上：分镜文字里出现的 「奶团」= 图片1、「户外草坪」= 图片2；同一主体在全片中保持同一外形，不得前后换脸 / 换犬种 / 换场地。
禁止：不得用参考图的静止姿势代替分镜要求的动作；不得把参考图中的其他元素当作主体；不得参考图之间的特征互相串用。
```

- **角色**只取外形，且**显式要求忽略参考图的静止姿势与机位** —— 这是参考图最容易带偏的地方（模型会把参考图的站姿/机位直接搬进片子）；实例特征从提示词里 `奶团（奶白短毛、黑鼻头、垂耳）` 的括号内自动抓取（≤40 字、不含换行）。
- 区块文本**不含 Markdown 星号**：提示词是纯文本，`**` 到了模型那里只是噪声。

| 登录命令 | `auth login` / `auth login --force`（清态重授权） | `login` / `relogin` / `logout` |
| 查账号 | `auth account` → `{userId, vipLevel, isVip}` | `user_credit` → `{total_credit, user_id, vip_level}` |
| 查积分 | **没有这个能力**（无 credit 命令） | `user_credit` |
| 实测 userId | **2251451286433180** | **3349575759569881** |

即：它既不是网页/App 的登录，也**不会换掉创作 CLI 的账号**；而界面上那个积分恰恰来自**创作 CLI**。

**实锤**：两个 CLI 的 `userId` 完全不同（`2251451286433180` ≠ `3349575759569881`）—— 也就是说**画布链路与创作链路走的是两个不同的即梦账号**，画布任务扣画布账号的积分，屏幕上那个数字只对创作 CLI 的任务有效。

#### 问题二：积分不但归属不清，数值本身还是陈旧的

后端显示 **105**，直接跑 CLI 拿到的是 **73**。

**根因**（`server/services.js adapterStatus` 的 fast 分支）：

```js
if (D && typeof D.peek === 'function') { Promise.resolve(D.peek() || D.probe(true)).catch(() => {}); }
...
(D && !cachedCanvas) ? D.probe() : Promise.resolve(D && D.peek ? D.peek() : null)
```

而 `peek()` **不判 TTL**——只要有缓存就返回真值。于是：

1. 后台刷新那行被 `peek()` 短路，`D.probe(true)` **永远不会执行**；
2. 结果 `dp` 又直接取自 `D.peek()`，绕过 60s TTL；
3. 净效果：**创作 CLI 的积分只在服务启动后读过一次，之后永不更新**（`adapterCheck` 也只强探画布，压根没碰创作 CLI）。

### 2.39 · fix: 素材提示词导入的两处缺陷（2026-09-19 12:20，待提交）

**缺陷 ①：「解析预览」成功后点「确认导入」必报「提示词文本为空」**

#### 二、设计要点

**新增 `server/task-state.js`**（状态迁移与写入权的唯一事实来源）：

- `ALLOWED` 迁移表固化**当前真实行为**（9 处状态写入点逐一登记），新增写入必须先在此登记；
- `canRetry` / `canCancel` / `isRunning` / `isTerminal` 供服务层判定；
- `newAttemptId()` / `ownsAttempt()` 供 worker 判权；
- `assertTransition()` 把"不该发生的迁移"变成响亮的失败，而不是静默写坏状态。

**worker 写入守卫** `guard(db, sb, attemptId, to)` —— 每个写入点前统一过闸，三种情况拒绝写入：

```
deleted        分镜已被删除（强制删除 / 批量删除）
stale-attempt  attemptId 已变（cancel 清空 / retry 换新 / 重新提交）
illegal        状态机不允许的迁移（如 canceled → succeeded）
```

被拒时**不再往该分镜的日志里写**（那正是幽灵数据本身），改写系统日志；若已拿到 `submit_id`，把它记进系统日志 —— 那是"钱已经花了"的唯一凭据，丢了就再也查不到。

**向后兼容**：历史数据没有 `attemptId` 字段时守卫自动跳过该项检查，行为与修复前一致。

### 2.49 · feat: 产物预览改真播放器 + 静态文件支持 HTTP Range（2026-09-19 20:20，待提交）

**用户上报**：「我产出的视频为什么我不能直接在产出物预览窗口预览它」。

**核实结论：不是"预览失败"，而是"预览从来就不是播放器"**。全项目 `grep "<video"` **零命中** —— 「产物预览」弹层渲染的是：

```html
<div style="height:260px;background:<渐变>">
  ▶(播放图标) + "16:9 · 5s · 720p" + "/files/st_…/…_video_1.mp4"(把地址当文字打出来)
</div>
```

这是**已知未实现项**：`docs/项目文档.md` §5.1 写的就是"产物预览：点击已完成行的结果缩略图，弹层展示封面渐变 + 视频地址（`videoUrl`）"。

**第二个原因（不修则播放器也白搭）**：静态文件服务不支持 HTTP Range。实测对产物地址带 `Range: bytes=0-1023` 请求，服务端回的是 **HTTP 200 + 全部 5385965 字节**（而非 206 + 1024 字节）—— 浏览器因此无法定位播放进度，拖进度条要重下整个文件。这正是问题清单 #13 的条目。

**改动**：

1. **`server/index.js` 的 `serveFile`**：`readFileSync` 整块读入 + 一次性写出 → **流式发送 + 单段 Range**。支持 `bytes=a-b` / `bytes=a-` / `bytes=-N` 三种形式，非法 Range 返回 `416`，一律带 `Accept-Ranges: bytes`；小文件（< 256 KB）仍一次读完，避免为一张缩略图多开一条流。`createReadStream` 挂 `error` 处理，避免传输中途文件被删导致未捕获异常。4 处调用点同步改为 `serveFile(req, res, p)`。
2. **`app/app.js`**：预览弹层改渲染 `<video controls preload="metadata" playsinline>`，附封面 poster 与「在新窗口打开 ↗」链接；新增 `mediaUrl()` 把后端返回的同源相对路径（`/files/…`）补上后端 origin —— 否则以 `file://` 打开的单文件发布版会把相对路径解析到本地磁盘。
3. **`app/styles.css`**：新增 `.pv-video` / `.pv-meta`。

**实测**：

| 检查项 | 结果 |
|---|---|
| 完整请求 | `HTTP 200` · `video/mp4` · 5385965 字节 |
| `Range: bytes=0-1023` | `206` · `Content-Length: 1024` · `Content-Range: bytes 0-1023/5385965` |
| `Range: bytes=1000000-` | `206` · 4385965 字节 · 从 1 MB 处到末尾 |
| `Range: bytes=-2048`（末尾 N 字节） | `206` · 2048 字节 · 末段 |
| 非法 Range（超出文件） | `416` |
| 浏览器：播放器加载 | `<video controls>` 存在 · **1280×720** · 时长 5.09s · `readyState=4` · 有 seekable 区间 |
| 浏览器：实际播放 | 播放 1.2s 后 `currentTime=1.11`（确实在推进） |
| 浏览器：拖动进度（依赖 Range） | 跳到 4.0s 后 `currentTime=4.84` ✓ |
| 预览弹层标题与说明 | 「产物预览 · 分镜 6」+「16:9 · 5s · 720p · 在新窗口打开 ↗」 |

**顺带**：无产物的分镜走「这条分镜还没有产物（未生成或已失败）」提示（防御性分支 —— 结果缩略图上的 `data-preview` 本就只挂在已完成行）。

### 2.51 · fix: CLI 未回传 submit_id 时自动找回 + parseJson 数组解析（2026-09-19 22:20，待提交）

**用户上报**：「我提交了一条生成为什么失败了」。

**核实**：seq 7 被标为 `failed`，`errorCode 50000`、`errorMessage = 创作 CLI 未返回 submit_id：get_history_by_ids failed: ret=1015, msg=`。

但**任务其实成功了** —— 用 `dreamina list_task` 查到：

```
submit_id: d32cc347-ef79-494c-9723-b329923d8a9b
gen_task_type: multimodal2video
gen_status: querying → success
credit_count: 30
benefit_type: dreamina_seedance_20_fast_5s   ← 确认用的是 Fast 模型
```

积分实测 2346 → **2316（扣 30）**，即**钱已花、任务已在即梦侧跑完**，只是 CLI 在回查那一步挂了、没把 `submit_id` 返回来。原实现遇到没有 `submit_id` 就直接判失败 ⇒ 用户白扔一次生成（而且视频其实已经生成好了）。

**两处修复**：

### 2.55 · fix: 框选时会选中文字（2026-09-20 02:10，待提交）

**用户上报**：「框选会选中文字怎么解决」。

**根因**：框选引擎里 `preventDefault()` 调用的**时机太晚**。原实现是：

```js
const onMove = (e) => {
  if (!armed) return;
  if (!dragging) {
    if (Math.abs(e.clientX - sx) < MARQUEE_THRESHOLD && ...) return;   // 4px 内不算拖拽
    dragging = true;
    ...
    e.preventDefault();      // ← 到这里才拦：阻止划词 / 原生拖拽
  }
```

而**浏览器的原生划词是在 `mousedown` 那一刻就开始建立选区的** —— 等鼠标移过 4px 再在 `mousemove` 里 `preventDefault`，选区已经建好，且对进行中的选区再调 preventDefault 取消不掉。于是拖拽框选的同时把卡片名称、行内文字一并选蓝了。

**修法**（`app/app.js` 的 `attachMarquee.onDown`）：把 `preventDefault()` 提到 **mousedown**，从源头阻止选区建立；并顺手 `getSelection().removeAllRanges()` 清掉拖拽前可能残留的选区（上一次划词的结果）。`onMove` 里原有的那次 preventDefault 保留作第二层。

**为什么不加 `user-select:none` 兜底**：那需要一个拖拽期间的全局类，一旦 mouseup 丢失（拖到窗口外松开）类会残留，用户就再也选不中任何文字 —— 风险大于收益。`preventDefault` 在 mousedown 是各家浏览器的标准做法，足够可靠。

**实测**：

| 检查项 | 结果 |
|---|---|
| 卡片 `mousedown` 被 preventDefault | ✓（这是"不产生原生划词"的关键） |
| 拖拽前预置选区（3 字）→ 按下后 | 选区被清空（长度 0）✓ |
| Tab 按钮 `mousedown` | 未被 preventDefault ✓（行为不受影响） |
| `.prompt-text`（提示词区）`mousedown` | 未被 preventDefault ✓（**划词复制能力保留**） |
| **回归：被 preventDefault 后 click 是否照常派发** | ✓ 模拟完整事件序列后素材编辑弹窗正常打开（名称「垃圾袋」）—— 证明没有打断点击链路 |
| 回归：合成框选仍生效 | ✓ 拖过 4 张卡片 → 已选 4、批量模式开启 |

**测试环境的限制（如实记录）**：本环境的 `cua.drag` / `cua.click` 已失效（探针显示 mousedown 与 click 计数均为 0，Playwright 的 locator.click 也超时），说明 IAB 标签页失去了前台焦点 —— 因此**原生划词的端到端拖拽测试无法在此环境执行**。上面的结论基于「事件属性 + 完整事件序列」的判定，而非一次真实鼠标拖拽。请在浏览器里实际拖一下确认。

- 想换一张，**多值槽位**（角色 / 道具）可以再点 `＋` 加一个、再把旧的 `×` 掉（绕）；**单值槽位**（场景 / 首帧图 / 分镜图）绑上之后 `＋` 就消失（`canAdd = meta.multi ? true : items.length === 0`），**根本没有换绑入口** —— 这正是用户此前报过"没有可用槽位"的同一处结构性问题。

**改法**（`app/app.js` + `app/styles.css`）：

1. `slotsHTML` 的 `.thumb` 加上 `data-bound="<assetId>" data-role="<role>"` 与 `clickable` 类（悬停加一圈主色描边，否则用户不知道这里能点）；`title` 补一句"点击预览 / 替换"。
2. 委托处理器在 `data-unbind` 分支**之后**新增 `data-bound` 分支。顺序是关键：`×` 是 `.thumb` 的子元素，点击按 DOM 层级先命中 `data-unbind`，所以"移除"语义不被抢走（已用合成事件实测：点 `×` 只解绑、不弹预览）。
3. 新增 `openBoundAsset(sb, role, assetId)`：原图直出（`object-fit:contain`）的预览弹窗，点图或悬浮钮进全屏；列出名称、类型与槽位、**图号**（并写出"提示词里用 `@图片N` 引用它"）；无图素材走半透明占位并提示「未计入图号」。
   - **文件被删、素材记录里还留着旧 `url`** 的素材（后端标成 `notCounted: 图片文件已丢失`）：`<img>` 会 404 成一张"碎图"。槽位用的是 `background-image`，404 看不见；预览弹窗里却能看见 —— 故给预览图挂 `error` 兜底：退化成同一套占位、摘掉 `zoomable` 与全屏钮、底部提示「图片文件读不到，可用「更换文件」补上」。
4. 两个替换入口，各自写明**作用范围**：
   - **替换素材** → `openAssetPicker(sb, role, {replace:true, replaceFrom})`，**只改本分镜的绑定**；
   - **更换文件** → `Api.replaceAsset`（保留素材 id 与全部分镜绑定），**所有引用它的分镜一起换**。
   两者差别用户最容易搞混，所以按钮 `title` 与弹窗正文里都各写了一遍。
5. `openAssetPicker` 新增 replace 语义：
   - 标题「替换素材 · 槽位」、提示「单选，确定后替换当前绑定的素材」、确定按钮文案「替换（N）」、底部提示「将替换为：…」；
