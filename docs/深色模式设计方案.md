## 一、令牌方案（A 阶段）

### 1.1 为什么必须先令牌化（核心前提，复述并强化）

现状是**一个「令牌驱动」的浅色主题，但驱动得不够彻底**：

- `:root` 的 **18 个颜色令牌只覆盖了"语义色"**（表面 / 墨色 / 强调 / 语义三态 / 分隔），
- 而**结构色**（表格斑马纹、行 hover、选中行、面板遮罩、媒体上的半透明控件底、行内 code 底、阴影、焦点白隙）**全部是硬编码字面量**，且大量散在 `app.js` / `index.html` 的**内联 SVG** 里。

后果：**只加 `[data-theme="dark"]{...}` 覆盖这 18 个令牌，另有 209 处不会翻转** ⇒ 深色下白底白字、白块、发光焦点环、浅色图标。

> **A 阶段的唯一目标**：把这 209 处（其中 CSS 121 处）**收敛为语义令牌或声明豁免**，且**浅色模式逐像素零变化**。B 阶段才补 `[data-theme="dark"]`。

### 1.2 命名规则

沿现有风格（`--surface/--parchment/--pearl/--ink/--ink80/--ink48/--primary/--primary-bg/--hairline/--divider/--chipgray/--ok(-bg)/--err(-bg)/--warn(-bg)/--track`），并遵守：

1. **一物一名，禁止语义重叠**：不新增 `--white`（与 `--surface` 重叠）、不新增 `--gray`（与 `--parchment` 重叠）。
2. **角色后缀约定**：`-bg` = 该语义的**浅色底**；`-ink` = 该颜色**作为文字**时的取值；`-600/-700` = 色阶步进。
3. **成对的语义类（`.hl-*` / `.b-*`）不拆令牌**（见 §1.4.4 决策）：它们是"前景+底色"两值绑定，令牌化反而增加 12 个低复用令牌，改用 **dark-only 规则覆盖**更克制。
4. **"永远位于深色底上"的颜色不令牌化**（见 §1.4.6 豁免清单）：如 `.codebox`、`.copywrap.on-dark`、全屏查看器、`.toast` 底——它们在两个主题下**都不该变**，令牌化是纯噪音。

### 1.4 必须处理的特例（逐项给处置规则）

#### 1.4.1 `--focus` 值内的 `#fff`（`styles.css:30`）

```
--focus:0 0 0 2px #fff,0 0 0 4px var(--primary);   /* 白隙 + 主色 */
```
- **问题**：令牌**值里**含字面量 ⇒ 覆盖 `--primary` 也救不了它；深色下白隙变成"发光白圈"。
- **处置**：拆出 `--focus-gap`（浅色 `#fff` / 深色 `= --surface`），`--focus` 改为
  `0 0 0 2px var(--focus-gap),0 0 0 4px var(--primary)`。
- **深色效果**：2px 的底色隙 + 4px 主色环，靠"底色隙"把主色环与控件隔开——与浅色同一视觉语法，不发光。

#### 1.4.2 阴影〔v1.1 订正：**否决"折入"，各留精确值令牌**〕

> **v1.0 的处置（把散落阴影折入 `--shadow-1/2`）已被否决。**原因：折入会**改变计算值**（例：`.menu` 的 `rgba(0,0,0,.12)` vs `--shadow-2` 的 `rgba(16,20,28,.12)`——色相不同；`.pj-card:hover` 的 `.06` vs `--shadow-1` 的 `.08`——透明度不同）。A 阶段的硬门禁是**逐像素零变化**，故**凡值不相等者一律各留独立令牌**。

A 阶段已把 6 处结构阴影**逐处令牌化、保留各自精确值**（`app/styles.css:73–78`）：

| 令牌 | 浅色精确值（＝原字面量） | 用途（选择器） |
|---|---|---|
| `--shadow-badge` | `0 1px 3px rgba(0,0,0,.28)` | `.thumb > .imgnum`（缩略图序号徽标） |
| `--shadow-menu` | `0 8px 24px rgba(0,0,0,.12)` | `.menu`（下拉菜单；**色相 ≠ `--shadow-2`**） |
| `--shadow-card` | `0 2px 10px rgba(0,0,0,.06)` | `.pj-card:hover`（项目卡 hover；**≠ `--shadow-1`**） |
| `--shadow-panel` | `-12px 0 32px rgba(0,0,0,.14)` | `.panel`（右侧素材抽屉） |
| `--shadow-detail` | `-12px 0 32px rgba(0,0,0,.12)` | `.rec-detail`（记录详情抽屉） |
| `--shadow-rail` | `6px 0 8px -6px rgba(0,0,0,.12)` | `.row > .cell.rail`（sticky 列） |
| `--shadow-1` | `0 1px 3px rgba(16,20,28,.08)` | 通用小阴影（既有） |
| `--shadow-2` | `0 8px 24px rgba(16,20,28,.12)` | 通用浮层阴影（既有） |

**深色策略（落到每个阴影上）**：深色下**阴影不靠"加深"承担抬升**——黑底上的黑色阴影**天然近乎不可见**（对比度 <1.5:1），再怎么加 alpha 也救不了；**抬升语义一律改由 1px `--hairline` 边框承担**，阴影只保留"一层极弱纵深"。据此：

### 2.2 主色在深底上的处理（含 `--primary-600/-700`）

**问题**：浅色里 `--primary`（`#0066CC`）**同时**充当"文字蓝"与"实心蓝"。深色下这两个角色**必须分家**：
- 作**文字**要够亮（对深底 ≥4.5:1）⇒ `#5AA9FF`；
- 作**实心按钮底**时上方是**白字**，白字要求底色够暗（≥4.5:1）⇒ `#0A6FD8`。

**取值与用途分工**：

| 令牌 | 浅色值 | 深色值 | 用途（谁用它） | 关键对比度 |
|---|---|---|---|---|
| `--primary` | `#0066CC` | `#0A6FD8` | `.btn-primary`/`.chips button.on`/`.pv-tab.on` 等**实心底**、`.cbx.on`、`.switch.on`、进度条 `i`、`.dot`、**边框**（`.btn-outline`/`:focus` 边框/inline focus `.input-sm:focus`）、`.zoom-btn:hover svg path`（stroke） | 白字 **4.91** ✅；对 surface **3.47** ≥3 ✅ |
| `--primary-ink` | **`#0066CC`**（与 `--primary` **浅色同值**） | `#5AA9FF` | 所有 **`color:` 蓝**（**19 处**〔v1.1 订正：含 `.crumb-link`〕，见 §1.3 表 1） | 对 surface **6.93** ✅ |
| `--primary-600` | `#0058B0` | `#0A5FBF` | **接替 `opacity:.9`**：`.btn-primary:hover`、`.copywrap .copy-btn:hover` | 白字 **6.17** ✅ |
| `--primary-700` | `#004C99` | `#0956AC` | `:active`（B 阶段新增） | 白字 **7.15** ✅ |

> **浅色侧显式说明（勿误读）**：浅色下 `--primary-ink` = **`#0066CC`**，与 `--primary` **完全同值**——即浅色的"一蓝两用"**尚未分家**，两个令牌指向同一色；**"分家"只发生在深色**（`--primary`→`#0A6FD8` 担实心/边框/环，`--primary-ink`→`#5AA9FF` 担文字）。工程师**不要**误以为浅色下 `--primary-ink` 也被赋了另一个值。

**`opacity` 压暗 → 色阶的替换**（B 阶段）：
- 现状 `.btn-primary{transition:opacity .15s}`(160) + `.btn-primary:hover{opacity:.9}`、`.btn-dark:hover{opacity:.88}`。
- `opacity` 的问题：深色下压暗实心蓝会让它**趋向背景色**（比浅色更不明显），且 `opacity` 会连带压淡上方白字。
- **替换为**：`.btn-primary:hover{background:var(--primary-600)}`（去掉 `opacity`），`:active{background:var(--primary-700)}`。深浅两主题中 `-600/-700` 均已各自达标（浅色：白字 5.57→6.8→7.5）。

> ⚠ **`opacity → -600` 属"可感知视觉变化"，必须放在 B 阶段**，不能混入 A 阶段（A 要逐像素零变化）。

## 三、主题切换机制（B 阶段）

### 3.1 三态：跟随系统 / 浅色 / 深色

**取值**：`auto`（跟随系统，默认）/ `light` / `dark`。

**"跟随系统"如何实现**（两选一，本文**推荐方案 B**）：

| 方案 | 做法 | 评估 |
|---|---|---|
| **A. 纯 CSS** | 不写 `data-theme`；用 `@media (prefers-color-scheme:dark){:root{...}}` | 简单，但**无法让用户显式覆盖**（一旦有 `[data-theme="dark"]` 覆盖，media 与属性选择器优先级打架，覆盖关系难维护） |
| **B. JS 解析后写 `data-theme`（推荐）** | 见下 | 单一事实来源，覆盖关系清晰 |

**推荐方案 B 的规则**：

1. **单一事实来源 = `document.documentElement`（`<html>`）上的 `data-theme` 属性**（`root` 令牌就在 `<html>` 上，`[data-theme]` 落同一元素最直观）。

   > 现有工程把令牌定义在 `:root`（= `<html>`）。**主题属性放 `<html>` 而非 `#app`**：因为 `.mask`/`.drawer`/`.recview`/`.pageview`/`.toasts` 都是 `#app` 的**兄弟/外部节点**（`index.html:94/97/136/154/218/…`），放在 `#app` 上它们拿不到。**这是必须遵守的结构约束。**

2. **解析流程（启动时，`bindStatic`/初始化早期，先于首帧渲染）**：
   - 读持久化值（§3.3）；无值则视为 `auto`。
   - `auto` ⇒ `const dark = matchMedia('(prefers-color-scheme:dark)').matches; html.dataset.theme = dark ? 'dark' : 'light'`。
   - `light`/`dark` ⇒ 直接写对应值（**用户显式选择优先于系统**）。
   - 同时挂 `matchMedia(...).addEventListener('change', ...)`：**仅当持久化值为 `auto` 时才响应**（否则用户的显式选择会被系统切换覆盖）。
3. **CSS 侧只需两条**：`:root{...浅色...}` 与 `[data-theme="dark"]{...覆盖...}`。**不写 `@media (prefers-color-scheme)` 进 CSS**（避免"媒体查询 vs 属性选择器"双源冲突）。
4. **防闪烁（FOUC）**：解析必须在首帧前跑。`index.html` 现有 `#app` 带 `hidden-view` 类、由 `setView()` 兜首屏——可在 `<head>` 末尾加一段**行内同步脚本**（早于 `app.js`），或在 `app.js` 顶部（模块执行期，早于 `bindStatic`）执行。**推荐前者**（`<head>` 内联 3 行读 localStorage 写 `data-theme`，杜绝刷新闪白）。

> **〔v1.1 实现补记 —— 用「双属性」而非单属性〕** 工程师在 B 阶段把方案 B 落成了**两个属性**，比 v1.0 的单属性更严谨：
> - `<html data-theme-mode>` = 用户的**选择**（`auto|light|dark`）——分段控件选中态读它；
> - `<html data-theme>` = 解析后的**实际主题**（`light|dark`）——**CSS 只认它**（`[data-theme="dark"]{...}`）。
>
> **为什么**：单属性存不下这三个值——`auto` 解析后必落到 `light` 或 `dark`，"用户显式选了浅色"与"用户选跟随系统、系统恰是浅色"就**无法区分**，分段控件便回显不出正确的选中项。**这是 v1.0 §3.1 的一处设计缺口，已由双属性闭合。**`initTheme()` 读 `localStorage['jmc.theme']` → `applyTheme()` 写这两个属性；`<head>` 内联脚本复刻同一逻辑（口径必须完全一致，否则会闪帧）。

### 3.2 落点：设置抽屉 →「个性化」分区，复用既有 `data-toggle` 分派

**现状（实测）**：

- 设置抽屉内容由 `renderSettings()` 用 `innerHTML` 生成（`app.js:4645` 起）。
- **「个性化」分区**在 `app.js:4703-4714`：一个 `.scard`，内有「紧凑视图」开关：
  ```html
  <span class="switch' + (isCompact() ? ' on' : '') + '" data-toggle="compact" ...><i></i></span>
  ```
- **分派机制**在 `app.js:5105-5115`（`#settingsBody` 的 `click` 委托）：
  ```js
  const tg = e.target.closest('[data-toggle]');
  if (tg) {
    const k = tg.dataset.toggle;
    if (k === 'autoRetry') S.settings.queue.autoRetry = !S.settings.queue.autoRetry;
    else if (k === 'compact') applyDensity(!isCompact());
    renderSettings(); return;
  }
  ```
- `isCompact()`/`applyDensity()` 在 `app.js:437-444`，**读状态读的是 `#app` 的 `.compact` 类本身**（"唯一事实来源"，注释明写"读类而不是另存变量"）。

**处置：完全复用这套机制，不新造并行开关。**

1. 在「个性化」卡片**「紧凑视图」行下方**再加一行「外观」：
   ```html
   <div class="srow"><span class="k">外观</span>
     <span class="seg" id="themeSeg">
       <button data-toggle="theme" data-theme-val="auto"  class="...">跟随系统</button>
       <button data-toggle="theme" data-theme-val="light" class="...">浅色</button>
       <button data-toggle="theme" data-theme-val="dark"  class="...">深色</button>
     </span></div>
   ```
   （三态用 `.seg` 分段控件；若嫌新样式，可先用三个 `.switch` 行——但**三态用分段控件更贴切**，`.seg` 样式已存在，见 `.seg button.on` 409。）
2. 在 `app.js:5105` 的分派里**加一个分支**（与 `compact` 平级）：
   ```js
   else if (k === 'theme') { setTheme(tg.dataset.themeVal); }
   ```
   > 注意：`.seg button` 的 `data-toggle` 与 `data-theme-val` 会同时命中——**判 `k === 'theme'` 后读 `dataset.themeVal`**；`renderSettings()` 会在末尾重绘以刷新选中态。
3. `setTheme(v)`：写 `html.dataset.theme`（`auto` 时按 §3.1 解析）+ 写持久化 + 同步 `.seg` 选中态。
4. **`isCompact()` 同源教训**：主题的**唯一事实来源是 `<html>` 的 `data-theme`**，`renderSettings()` 渲染选中态时**读 `html.dataset.theme`**，不要另存 `S.theme` 变量作为真相（`S.theme` 可只作持久化镜像）。

### 3.3 持久化

**关键事实（纠正简报）**：**全仓库 `app/` + `server/` 目前 `localStorage`/`sessionStorage` 用量 = 0**（实测 `grep -rn`）。紧凑视图**明确不持久化**——`app.js:4712` 原文："此项为即时生效的显示偏好，**不写入服务端配置，刷新后回到标准视图**"。

⇒ **不存在"既有 localStorage 命名约定可复用"**。本方案**新立约定**，并建议**顺带把紧凑视图也持久化**（同一 key 命名风格，避免"一个持久化一个不持久化"的割裂）。

| 项 | 约定 |
|---|---|
| key 前缀 | `jmc.`（即梦控制台缩写，全小写点分） |
| 主题 key | **`jmc.theme`** |
| 紧凑视图 key | **`jmc.compact`**（可选增强，值 `"1"`/`"0"`） |
| 值域 | `jmc.theme` ∈ {`"auto"`,`"light"`,`"dark"`}；非法值一律回落 `"auto"` |
| 读时机 | ① `<head>` 行内脚本（仅读 `jmc.theme`，写 `data-theme`，防 FOUC）；② `app.js` 初始化（读 `jmc.compact` → `applyDensity`） |
| 写时机 | `setTheme()` / `applyDensity()` 内，**改动即写**（即时生效偏好，与设置抽屉的「保存设置」解耦） |
| 容错 | `try/catch` 包裹（隐私模式下 `localStorage` 可能抛错）；读失败回落默认，写失败静默 |
| 与「保存设置」的关系 | **主题/紧凑不进服务端 `PUT /settings`**（它们是"本页外观偏好"，与生成参数无关；与现有 `compact` 的语义保持一致） |

### 5.1 漏改导致深色局部破相（**最高风险**）

- **成因**：209 处字面量散落在 CSS + JS 内联 SVG + HTML 内联 style 三处；漏一处 = 深色下留一个浅色斑。
- **机械化自检（必须纳入 CI/验收命令）**〔v1.1 订正：**必须用「按选择器判定的豁免白名单」版脚本**〕：规定 **`:root` 与 `[data-theme="dark"]` 块之外，`app/styles.css` 不得出现任何非豁免的 hex/rgba**。

### 7.6 原生控件的 `color-scheme`〔v1.2 补记：B 阶段实测新增〕

> **现象**：B 阶段首轮深色截图发现——**未设显式 `background` 的原生控件，在深色下仍渲染白底**：设置抽屉里 **4 个 `<select>`** 全白。同类还有 `.input-sm`、`.modal-body textarea` 等**依赖 UA 默认外观**的控件。

**为什么"光覆盖 CSS 令牌"解决不了**：

- 这些控件**没有显式 `background`**（或仅设了 `color`），其底色/边框/文本色、以及下拉箭头、日期选择器面板等，**全部由用户代理（UA）的默认外观决定**；
- 而 UA 默认外观的**明暗**由 **`color-scheme`** 这一 CSS 属性决定——它**不是**我们的 `:root` 令牌，**覆盖再多 `--surface`/`--ink` 令牌也管不到它**；
- 后果：`body{background:var(--surface)}` 已翻成深色，但 `<select>` 内部仍按"UA 浅色"绘制 ⇒ 深色页面上一个刺眼的白块。**这是"令牌体系之外"的一类缺陷，与 §5.1 的"漏改令牌"不同源。**

**修法（已落地，两行、零字面量）**：

```css
:root{ color-scheme:light; }              /* 写在浅色令牌块内 */
[data-theme="dark"]{ color-scheme:dark; } /* 写在深色令牌块内 */
```

- 两行**分别写在两个令牌块内部**（浅色写 `:root`、深色写 `[data-theme="dark"]`），与其它令牌同处一源；
- **不引入任何 hex/rgba 字面量** ⇒ `_check.js` 的豁免白名单**无需放宽**（仍 **18 条**，§7.1 第 3 条红线不破）；
- 命中范围：原生表单控件（`input`/`textarea`/`select`/日期选择器）、滚动条、选区高亮、光标 `caret`、默认按钮——**凡"依赖 UA 默认外观"者一并跟随**。

**实测（深色计算样式，逐项核对）**：

| 控件 | `background` | `color` | `color-scheme` | `border-color` |
|---|---|---|---|---|
| `select` ×4（设置抽屉） | `rgb(59,59,59)` | `rgb(245,245,247)` | `dark` | `rgb(58,58,60)` |
| `textarea`（`.modal-body`） | `rgb(59,59,59)` | `rgb(245,245,247)` | `dark` | `rgb(58,58,60)` |

**浅色侧也必须显式声明 `color-scheme:light`（关键，勿省）**：

- 只声明深色侧是不够的——**浅色 `:root` 若不给 `color-scheme`，UA 会回落到"跟随操作系统偏好"**；
- 于是当 **OS 为深色、而应用为浅色**时，原生控件被 UA 反向绘成**深色**（浅色页面上一撮黑块）——它与"深色页白块"是**同一类缺陷的镜像**；
- 显式 `color-scheme:light` 把浅色侧**钉死**在浅色 UA 外观，**不再受 OS 偏好反向影响**（更稳）。
