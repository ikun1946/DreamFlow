# 安装包换前缀 · 第二步操作清单

> 状态：现行（待执行 —— `0.31.0` 已发布，第二步等时机；执行完请删除本文件）
>
> 适用版本：`0.31.0` 之后（第一步已完成）。本文件是**执行清单**，不是变更记录 ——
> 执行完请把结果写进 `docs/CHANGELOG.md` 对应版本，并删除本文件。
>
> 背景与决策依据见 `docs/CHANGELOG.md` 的 `0.31.0` 一节；代码内设计说明见
> `desktop/updater.js` 的「产物名换前缀：必须分两步」注释块。

## 前置条件（不满足就不要执行）

**必须在 `0.31.0` 已被目标用户群体消化之后再发第二步。**

原因：`0.31.0` 唯一的作用就是让用户机器上的更新器变成「双前缀都认」。
如果 `0.31.0` 刚发布、用户还停在 `≤ 0.30.0`，此时发第二步，那些用户仍会
「找到更新 → 下载完成 → 校验拒绝」，**结果和一次改完没有区别**，第一步就白做了。

判断是否可执行的两个依据：

1. `0.31.0` 的 Release 已发布一段时间（建议至少数天）；
2. 没有已知的活跃用户停留在 `≤ 0.30.0`。

> 无法确认时，保守做法是**继续等**。第二步不着急 —— 它只是让安装包文件名更统一，
> 不影响任何功能。

## 要改的 4 处（不多不少）

### ① `electron-builder.yml` —— 3 个值

```yaml
# 第 75 行附近（win: 段内）
executableName: DreamFlow                  # 原 JimengConsole

# 第 142 行附近（nsis: 段内）
artifactName: DreamFlow-${version}-x64-Setup.${ext}      # 原 JimengConsole-

# 第 146 行附近（portable: 段内）
artifactName: DreamFlow-${version}-portable.${ext}       # 原 JimengConsole-
```

### ② `desktop/updater.js` —— 2 个值

```js
// 当前产物前缀 → 改成 DreamFlow-（必须与 yml 一致，门禁会比对）
const ARTIFACT_PREFIX = 'DreamFlow-';

// 列表顺序调换：把新前缀放第一位；**旧的 JimengConsole- 必须保留**！
// 原因：老用户机器上可能残留 JimengConsole-*.part-* 临时文件（每个 100+ MB），
// cleanupStaleTemp 靠它才能清掉。
const ACCEPTED_PREFIXES = ['DreamFlow-', 'JimengConsole-'];
```

### ③ `test/03-build-release.test.js` —— 2 处断言

```js
// 1) 第一条用例里
assert.equal(updater.ARTIFACT_PREFIX, 'JimengConsole-');   // → 'DreamFlow-'

// 2) 同一用例里的 yml 形状断言
assert.match(yml, /artifactName:\s*JimengConsole-\$\{version\}-x64-Setup\.\$\{ext\}/, ...);
// → /artifactName:\s*DreamFlow-\$\{version\}-x64-Setup\.\$\{ext\}/

// 3) ACCEPTED_PREFIXES 的 deepEqual 断言 —— 顺序要与 ② 一致
assert.deepEqual(updater.ACCEPTED_PREFIXES, ['JimengConsole-', 'DreamFlow-']);
// → ['DreamFlow-', 'JimengConsole-']
```

> 双前缀用例里的 `stillBad` 列表**不用改** —— 那些断言针对的是「非法前缀必须被拒」，
> 与当前前缀是谁无关。

### ④ 版本号 → `0.32.0`（两处三地）

- `package.json` 的 `version`（**唯一生效来源**）
- `README.md`：顶部表格「当前版本」+ 「当前版本：**`x.y.z`**」两处
- `AGENTS.md`：首行「最后核对」
- `docs/项目文档.md`：适用版本 / 当前版本 / 末行核对 三处
- `docs/CHANGELOG.md`：新增 `0.32.0` 一节
- `README.md` 第 3-5 行那段命名说明要**更新**（那时安装包已叫 `DreamFlow-*`，
  不再需要「为什么叫 JimengConsole」的解释）

## 不用改的（避免白费功夫）

- **`scripts/check-project.js`** —— `0.31.0` 已把 §4 的门禁改成「从源码提取
  `ARTIFACT_PREFIX` 再比对 yml」，换名时**自动跟随**；同时仍会强制上面 ① 与 ②
  必须一起改。这是刻意的设计。
- **`scripts/check-signing.js`** —— 已同时识别两种 exe 名。
- **`appId`** —— 不改。它决定 Windows 能否识别「同一个应用」、能否原地升级。
- **`productName`** —— 不改（中文产品名，决定 userData 目录名）。
- **`desktop/runtime-paths.js` 的 `DATA_FOLDER_NAME`** —— 不改。数据目录一旦改名，
  用户打开新版会以为「项目全没了」。这是唯一会碰真实数据的改动，**不属于本次范围**。

## 执行步骤

```bash
# 1) 改上述 4 处
# 2) 自检（门禁会校验 yml 与 updater 的前缀一致）
npm run check && npm run lint && npm test

# 3) 反向验证（照例必做）：把 yml 的 artifactName 改成 JimengConsole- 而 updater 不改，
#    确认门禁报「前缀不一致」；然后改回。不做这步无法区分「真的通过了」和「扫不到」。
# 4) app/ 未改动，dist/ 无需重建
# 5) 打包（输出到仓库外目录，避开本机的删除保护）
npm run dist -- --config.directories.output="%TEMP%/jc-rel-0320" --publish never
# 6) 校验 latest.yml 的 sha512 / size 与安装包实际值一致，PE 头为 MZ
# 7) 确认 win-unpacked 下的主程序已叫 DreamFlow.exe
# 8) 提交 + 推送 + 打 tag v0.32.0（tag 必须单独 push）
# 9) 发布 Release（三个附件：exe / latest.yml / blockmap）
# 10) 端到端验证：check('0.32.0') → hasUpdate=false；check('0.31.0') → hasUpdate=true
# 11) 把结果写进 CHANGELOG，删除本文件
```

## 第二步发布后，用户会经历什么

| 项 | 变化 |
|---|---|
| 安装包文件名 | `DreamFlow-0.32.0-x64-Setup.exe` |
| 可执行文件 | `DreamFlow.exe` |
| **安装目录** | `%LOCALAPPDATA%\Programs\JimengConsole\` → **`Programs\DreamFlow\`** |
| 快捷方式 | 重建（指向新 exe） |
| 任务栏固定项 | 可能失效，需重新固定 |
| 升级方式 | 靠 `appId` 的 GUID 识别已装实例，**不会新旧并存**，但会「先卸后装」 |
| **用户数据** | **不受影响** —— 在 `%USERPROFILE%\Videos\JimengConsole\`，卸载时明确不删 |
| `appId` / 数据目录 | 不变（刻意保留） |

> 安装目录随 `executableName` 变的依据是实测：`0.25.0` 装在
> `%LOCALAPPDATA%\Programs\JimengConsole\`，而不是 `Programs\即梦批量生成控制台\`
> —— 即 NSIS 的默认安装目录用的是 `executableName`，不是 `productName`。

## 风险与回退

- **风险**：某用户长期停留在 `≤ 0.30.0` 且从不升级 → 第二步发布后他会「看到更新但装不上」。
  这类用户需**手动下载安装一次**（与 `≤ 0.25.0` 用户的情况相同，见
  `docs/版本发布与更新流程.md` 的引导一节）。
- **回退**：第二步的改动集中在上表 4 处，把 `ARTIFACT_PREFIX` 与 yml 改回
  `JimengConsole` 即可回到 `0.31.0` 的行为；**`ACCEPTED_PREFIXES` 保留两种前缀不要动**
  （它同时服务向前与向后兼容）。
