## 一、先说清「请求地址 / 请求体」这件事

提交视频生成在我们系统里分两层，**只有第一层是 HTTP**：

| 层 | 谁 → 谁 | 形态 | 地址 / 体 |
|---|---|---|---|
| ① 前端 → 我们的后端 | 浏览器 → 本机服务 | **HTTP POST** | `POST http://127.0.0.1:8787/api/v1/storyboards/batch-submit`，体 `{"ids":["st_efb1cdaf"]}` |
| ② 我们的后端 → 即梦 | Node 服务 → CLI 子进程 | **进程调用（无 HTTP、无请求体）** | `spawn("dreamina-canvas", argv, {windowsHide:true, shell:false})` |

**关键点**：我们的后端**不直接向即梦发 HTTP 请求**，也不存在"请求体"。它把参数拼成 CLI 的 argv 后启动子进程；**真正与即梦服务端通信（含鉴权、报价、提交）全部由 CLI 内部完成**，其上游地址与报文 CLI 未对外暴露（CLI 只暴露 JSON 信封与退出码）。

所以"核对提交时发送的命令"，要核对的正是**第 ② 层的 argv**——即下面这条。

## 二、真正会执行的完整命令（画布 CLI）

```bash
dreamina-canvas --format json --non-interactive --region cn \
  node create video --run --wait \
  --submit-id 0112e5f3-07da-45dd-8a34-da729ed87349 \
  --mode t2v \
  --credit-ceiling 200 \
  --prompt 近景，相机固定在小狗的头上，小狗从一个圆形的圆圈中跳过 \
  --model seedance_2.0_fast_vip \
  --duration 4 --ratio 16:9 --resolution 720p
```

### argv 逐项说明

| # | 参数 | 值 | 来源 / 作用 |
|---|---|---|---|
| 0–1 | `--format json` | — | 全局：输出 JSON 信封，后端据此解析（`server/cli.js` 的 `withGlobals()`） |
| 2–3 | `--non-interactive` | — | 全局：禁用交互提示（后端无人值守） |
| 4–5 | `--region cn` | — | 全局：产品区域，来自 `server/config.json` |
| 6–7 | `node create video` | — | 子命令：在画布上创建视频节点 |
| 8 | `--run` | — | 保存后依次**报价 → 批准 → 运行**（报价超上限会停在运行前，不扣费） |
| 9 | `--wait` | — | 阻塞等待该节点生成进入终态 |
| 10–11 | `--submit-id` | `<uuid>` | **后端先生成并落盘**（`db.cliJobs[id].submitId`）再启动进程——这是崩溃/停顿后**幂等续跑**的钥匙，重试必须复用同一条 |
| 12–13 | `--mode` | `t2v` | **生成模式（必填）**。规则：无可用视觉引用 → `t2v`；有首帧/分镜图引用 → `first_last_frame`；其余有图引用 → `m2v` |
| 14–15 | `--credit-ceiling` | `200` | **积分上限安全阀**，来自 `server/config.json` 的 `creditCeiling`；报价超过即停，不扣费 |
| 16–17 | `--prompt` | 分镜提示词 | 来自分镜字段，逐字传入 |
| 18–19 | `--model` | `seedance_2.0_fast_vip` | 分镜所选模型（名称已按画布实时目录归一） |
| 20–21 | `--duration` | `4` | 分镜时长（秒），已按该模型规格收敛 |
| 22–23 | `--ratio` | `16:9` | 分镜画幅，已按该模型规格归一 |
| 24–25 | `--resolution` | `720p` | 分镜分辨率，已按该模型规格归一（该模型仅支持 720p） |

> 若分镜绑定了**已登记到画布的素材**（即素材带有 `cliNodeId`），还会追加若干 `--ref node:<nodeId>`；本次两个素材是本地直接上传、尚未登记到画布，因此没有 `--ref`（见第五节"已知限制"）。

## 三、CLI 的本地校验结果（证明这条命令合法）

对同一条 argv 追加 `--dry-run` 后由 CLI 自行校验，返回：

```json
{
  "ok": true,
  "data": {
    "dryRun": true,
    "validationScope": "local",
    "sideEffects": [],
    "plan": {
      "steps": ["save", "quote", "approve", "run"],
      "generation": { "mode": "t2v", "prompt": "近景，相机固定在小狗的头上…", "model": "seedance_2.0_fast_vip",
                      "ratio": "16:9", "resolution": "720p", "durationSeconds": 4, "outputCount": 1 },
      "submission": { "identity": { "value": "0112e5f3-…", "source": "explicit" }, "usesCreditToken": false,
                      "creditCeiling": 200, "waitForTerminal": true, "timeout": "10m0s", "interval": "5s" }
    },
    "unverified": ["authentication", "project_access", "authoritative_draft_state",
                   "current_project_context_resolution", "model_specification",
                   "credit_quote", "credit_balance_and_authorization", "dispatch_and_generation"]
  }
}
```

- `sideEffects: []` —— 本地校验**没有任何副作用**（未写草稿、未报价、未扣费）；
- `unverified` 八项 —— 只有真正连服务端才能确认的部分（鉴权、项目权限、真实报价与余额、实际派发与生成）。这正是"不连即梦"与"真跑"的分界线。

## 四、同一分镜若走创作 CLI（对照）

自动路由在「通用模型 + 无音频」时选画布 CLI；若该分镜绑定了音频，或模型仅创作 CLI 支持，则命令变为：

```bash
dreamina multimodal2video \
  --prompt 近景，相机固定在小狗的头上，小狗从一个圆形的圆圈中跳过 \
  --duration 4 --ratio 16:9 --video_resolution 720p \
  --model_version seedance2.0fast_vip --poll 30 \
  --image "<本地素材1路径>" --image "<本地素材2路径>"
```

差异要点：创作 CLI 会把**本地图片/音频自动上传**并作为参考（`multimodal2video`），但它**没有 `--dry-run`**，也没有报价→确认的积分安全阀（所以默认优先画布 CLI）。

## 五、本次核对发现并修复的 4 个缺陷

用 CLI 自带的 `--dry-run` 逐字校验命令时，暴露了 4 个"一提交就失败"的真实缺陷：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | **缺 `--mode`** | CLI 直接拒绝：`cli.generation_mode_required`（"Specify a non-empty --mode…"） | 新增 `resolveMode()`，按分镜可用引用推断模式并校验模型是否支持 |
| 2 | **缺 `--credit-ceiling`** | 配置里的积分上限（200）实际从未下发，"报价→确认"安全阀形同虚设 | 组装命令时下发该参数 |
| 3 | **flag 前缀重复（`----prompt`）** | 模型规格里的 flag 自带 `--` 前缀，又被补了一次 → 命令非法 | `pickFlag()` 统一剥前缀，并在组装末尾加自检：出现 3 个以上连字符直接拦截报错 |
| 4 | **`buildArgs` 里 `db` 是未声明变量** | 凡**绑定了素材**的分镜一律 `ReferenceError`（worker 报"worker 异常"失败）；未绑素材的分镜因循环体不执行而侥幸不报错 | `db` 改为显式参数传入 |

修复后复验：同一条命令 `ok: true`、`exitCode: 0`，`plan.steps = save → quote → approve → run`。

**已知限制（未修，需你决定）**：画布 CLI 只能引用**已登记到画布的素材**（`--ref node:<nodeId>`），而目前「本地创建/导入的素材」只落在我们自己的素材库与磁盘上，**没有登记进画布**——所以画布引擎生成时不会用到这些图片；同一条分镜改用创作 CLI 则会自动上传并引用。若要画布链路也吃到本地素材，需要新增一步"素材登记到画布"（CLI 的 `resource upload`）。

## 六、如何复跑这次核对（零消耗）

```bash
# 1) 干跑校验：返回路由结果 + 各引擎命令 + CLI 本地校验（不提交、不改任务状态）
curl -X POST http://127.0.0.1:8787/api/v1/storyboards/<分镜ID>/dry-run \
     -H "Content-Type: application/json" -d '{}'

# 2) 只想要命令、不让 CLI 校验（更快）：
curl -X POST http://127.0.0.1:8787/api/v1/storyboards/<分镜ID>/dry-run \
     -H "Content-Type: application/json" -d '{"cliDryRun": false}'

# 3) 让"正常的提交链路"也只组装不执行（整服务生效，用完记得切回）：
JC_DRY_RUN=1 node server/index.js
#   此时点"提交所选"：worker 会记录命令并写日志，但不会 spawn 任何进程，
#   任务状态回到「未提交」，命令可在分镜详情的「将要执行的 CLI 命令」里看到。
```
