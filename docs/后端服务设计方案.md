## 1. 目标与设计原则

1. **前端零改动**：前端已在 `api.js` 预留 `window.APP_CONFIG = { apiMode: 'http', baseUrl, token, projectId }`。后端按契约实现后，改一行配置即可切换，`app.js` 不动。
2. **契约即法律**：23 个接口的路径、请求体、响应信封、错误码与《前端页面与接口对接说明.md》逐字一致；前端 `httpRoute()` 只做「信封解包 + `code !== 0` 抛 `ApiError`」，后端必须保证信封结构。
3. **CLI 是唯一生成通道**：后端不直连即梦 HTTP 端点，全部通过本地 `dreamina-canvas` CLI（`--format json --non-interactive`）交互，遵守其协议：先报价后扣费、submitId 幂等恢复、受理 ≠ 完成。
4. **本地单用户服务**：服务与 CLI 同机部署，监听 `127.0.0.1`，默认不做多租户（契约 8.7：保留 `projectId` 占位）。

## 2. 技术选型与运行形态（v1.1 实现定稿）

> **实现取舍说明**：原方案 Express + better-sqlite3；实现时改为 **Node 内置模块（零 npm 依赖）+ JSON 原子写持久化**。原因：单用户本地桥接服务无需框架与原生模块（规避 Windows 下 better-sqlite3 的 node-gyp 编译风险），与本项目「零依赖」的工程哲学一致。分层结构与接口行为不受影响。

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js ≥ 20 | 与 `build.js` 同栈；`child_process.spawn` 调 CLI；**零 npm 依赖**（node:http / node:crypto / fs） |
| Web 层 | 内置 `http` + 自写路由表（`server/routes.js`） | 仅 23 条路由，无需框架；统一信封由 `util.js` 的 ok/fail 保证 |
| 持久化 | JSON 文件 `server/data/db.json`（临时文件 + rename 原子写） | 任务状态跨进程、跨重启存活；单用户本地场景够用 |
| 任务存储补充 | `db.cliJobs`（每任务的 CLI 身份字段，随 db 持久化） | 承载 CLI 要求的最小 job state（Node ID / submit ID / Resource ID） |
| 产物存储 | `server/data/projects/{projectId}/output/{storyboardId}/` | 视频与封面下载落盘，由 `/files/{projectId}/{storyboardId}/` 静态路由对外提供 `videoUrl`。**2026-09-20 起资源按项目分目录**（原先平铺在 `data/output/`）：归属由目录结构保证，彻底删除项目 = 删掉 `data/projects/{projectId}/` 一个目录 |
| 端口 | `127.0.0.1:8787` | 本机服务；CORS 允许 `file://` 与本地静态源（前端可能双击打开或 `npx serve`） |
| 进程模型 | 1 个 HTTP 进程 + 1 个内存队列（并发 worker 上限 = `settings.queue.concurrency`） | 单机批处理场景，无需独立任务队列中间件 |

启动：

```bash
node server/index.js          # 或 pm2 / 计划任务常驻
# 前端接入：
# window.APP_CONFIG = { apiMode:'http', baseUrl:'http://127.0.0.1:8787/api/v1', projectId:'pj_1' }
```

## 3. 总体架构

```
┌───────────── 浏览器：app/index.html + app.js ─────────────┐
│   只依赖 window.Api（app/api.js，apiMode='http'）          │

                            │ fetch /api/v1/*（Bearer token 可选）
┌───────────────────────────▼──────────────────────────────┐
│  HTTP 层（Express Router，23 条路由，统一信封 + 错误中间件）│
├───────────────────────────────────────────────────────────┤
│  服务层                                                   │
│   StoryboardService / AssetService / SettingsService /    │
│   ImportService / MetaService / AdapterService            │
├───────────────────────────────────────────────────────────┤
│  执行层                                                   │
│   QueueScheduler（并发闸、autoRetry）                      │
│   TaskWorker（每任务一条状态机，见 §7.3）                   │
├───────────────────────────────────────────────────────────┤
│  CLI 适配层 CliAdapter（唯一 spawn 出口）                  │
│   spawn 封装 / JSON 信封解析 / 退出码分类 / 超时 / 探测     │
└───────┬───────────────────────────────┬───────────────────┘
        │                               │
        ▼                               ▼
  dreamina-canvas CLI             SQLite + job-state + output/
  （本机已登录账号）               （状态持久化与产物落盘）
```

分层纪律与前端同构：**HTTP 层不碰业务规则，服务层不碰 spawn，CliAdapter 不碰 SQL。**

## 4. 前端接入与通用约定

- **Base URL**：`http://127.0.0.1:8787/api/v1`。
- **认证**：可选 `Authorization: Bearer <token>`。本地单用户模式下 token 由后端启动时打印（或固定配置），校验失败返回 `40100`。前端 401 只 Toast 不跳登录（已知边界），后端照常返回正确码。
- **统一响应信封**（必须，前端 `httpRoute()` 依赖）：

```jsonc
{ "code": 0, "message": "ok", "data": { }, "traceId": "a1b2c3d4" }
```

- HTTP 状态码只表达传输层语义；业务成败看 `code`。错误码表与契约 0.3 一致（`40001/40100/40300/40400/40900/42900/50000/51001–51005`）。
- **幂等**：`POST /storyboards/batch-submit` 与 `POST /storyboards/import` 必须实现 `Idempotency-Key` 请求头（前端已在 `api.js` 中随请求发送，`rid('')` 生成）；同一 key 重放返回首次结果。
- **时间格式**：ISO 8601 带时区；**ID 前缀**：分镜 `st_`、素材 `as_`、项目 `pj_`、批次 `bt_`、即梦远端 `jm_`。
- **CORS**：`Access-Control-Allow-Origin: *` + 允许 `Authorization / Idempotency-Key / Content-Type` 头（前端可能从 `file://` 打开）。

## 5. 数据模型与状态机

### 5.1 表结构（SQLite）

```sql
storyboards(
  id TEXT PRIMARY KEY,            -- st_xxx
  project_id TEXT, batch_id TEXT, seq INTEGER,
  prompt TEXT, negative_prompt TEXT,
  duration_sec INTEGER, model TEXT, ratio TEXT, resolution TEXT,
  seed TEXT, motion REAL,
  status TEXT CHECK(status IN ('queued','generating','succeeded','failed','canceled')),
  progress INTEGER, eta_seconds INTEGER,
  remote_id TEXT,                 -- jm_xxx：CLI 侧 submitId 的业务映射（展示用）
  video_url TEXT, cover_url TEXT, current_frame_url TEXT,
  elapsed_ms INTEGER, retry_count INTEGER,
  error_code TEXT, error_message TEXT,
  can_edit_duration INTEGER,
  dirty INTEGER DEFAULT 1,        -- 轮询增量标记（§6.2）
  created_at TEXT, started_at TEXT, finished_at TEXT
)
storyboard_assets(storyboard_id, asset_id, role, PRIMARY KEY(storyboard_id, asset_id, role))
assets(id TEXT PRIMARY KEY, project_id TEXT, name TEXT, type TEXT,
       url TEXT, thumb_url TEXT, width INTEGER, height INTEGER, tags TEXT,
       cli_node_id TEXT, cli_resource_id TEXT)   -- CLI 身份缓存（§7.2）
settings(id=1, json TEXT)        -- delimiter / defaults / queue / adapter.mode
idempotency(key TEXT PRIMARY KEY, response_json TEXT, created_at TEXT)
cli_jobs(                        -- 最小 job state（CLI 规范要求持久化的身份字段）
  storyboard_id TEXT PRIMARY KEY,
  canvas_id TEXT, node_id TEXT, update_id TEXT,
  submit_id TEXT,                 -- UUID，运行前预生成落盘（§7.4）
  operation_ref TEXT, selected_resource_id TEXT,
  authorized_ceiling INTEGER,     -- 该 item 已批准的积分上限
  attempt INTEGER, state TEXT, updated_at TEXT
)
```

> job state 只保存持久公开身份与授权上限；**绝不持久化** credit token、signed URL、provider payload（CLI 硬边界）。

### 5.2 状态机与 CLI 阶段映射

```
queued ──worker 取件──► generating ──资源终态成功──► succeeded
   ▲                       │                            
   │retry                  ├─被拒/超限/策略──► failed    
   └───────────────────────┴─用户取消(仅未派发)──► canceled
```

| 本地 status | CLI 侧事实 |
|---|---|
| `queued` | 已入库、等待并发闸；未发生任何 spawn |
| `generating` | `node create … --run` 已受理（拿到 submitId），`operation` 运行中 |
| `succeeded` | 已看到资源终态成功 + 选中 Resource ID，视频/封面已下载落盘 |
| `failed` | 终态 `rejected`/`failed`、报价被拒、重试耗尽（附 `errorCode/errorMessage`） |
| `canceled` | 仅允许**尚未 spawn** 的任务；运行中无法真正取消（§7.6 如实说明） |

`canEditDuration` 由服务端裁决：`status !== 'succeeded'`（与 mock 行为一致，契约 8.2 默认锁定已完成项）。

## 6. API 接口定义（23 个）

以下逐一给出**后端实现要点**；请求/响应结构与契约文档第 4 章逐字段一致，此处只列关键示例。所有响应都套统一信封。

### 6.1 元数据与系统

**① `GET /meta/options`** — 枚举与边界，前端不硬编码。实现：静态配置（ratio/resolution/duration 边界、分隔符预设、并发 1–5、重试上限 2）∪ **实时模型目录**（`CliAdapter.modelList('video')`）。每个模型：`value` 用 canonical model（`model list` 返回的 `model` 字段，禁止用 alias 入参）、`label` 展示名、`enabled`/`disabledReason` 由 `isVip`/`vipConfigs[]` 与当前账号会员态（`auth account`）推导——契约里 `seedance-2.0-fast` 带 `disabledReason: '当前账号未开通'` 即此机制。`duration.min/max` 必须下发（前端步进器边界依赖它；⚠ 各模型实际上限以 `model list` 的 flags 为准，不同模型可不同，取交集或按当前默认模型下发）。CLI 不可用时回退纯静态配置并在 `system/adapter` 里体现降级。

**② `GET /auth/me`** — 单用户占位：`{ userId:'u_1', name:'本地用户', credits:null, plan:'local' }`。前端 `Api.me()` 已定义但 UI 未调用，保持契约兼容即可。CLI 无积分余额查询命令，`credits` 返回 null，不编造。

**③ `GET /system/adapter`** — 返回 `{ mode, cliAvailable, cliVersion, checkedAt, message }`。实现：`AdapterService` 缓存探测结果（30s TTL）：`spawn('dreamina-canvas --format json version')` + `auth status`（`loggedIn:true` 才算 available）。前端每 30s 轮询本接口（契约 4.1.5 ⑧），后端探测必须轻量、失败不抛 5xx（正常信封返回 `cliAvailable:false` + message）。

### 6.2 分镜 CRUD 与列表

**④ `GET /projects/{projectId}/storyboards`** — 兼容 `GET /storyboards`（mock 双路由同名）。参数 `page/pageSize/status(逗号多选)/keyword(命中 prompt|id|remoteId)/batchId/sort`。响应 `{ list, page, pageSize, total, stats }`，**stats 内联**（顶栏与状态栏共用，契约明确不接受两次串行请求）。`stats.etaSeconds = 剩余任务数 × 历史平均耗时 ÷ concurrency`。每次返回把行 `dirty` 清零。

**⑤ `GET /storyboards/progress?ids=st_1,st_2`** — 轮询接口（3–10s 高频）。**只返回 `dirty=1` 的行**，无变化返回 `data: []`（前端据此退避）。单次 `ids` ≤ 50。返回字段：`id, status, progress, etaSeconds, currentFrameUrl, videoUrl, coverUrl, retryCount, errorCode, errorMessage, canEditDuration`。进度由 TaskWorker 写库置 dirty，本接口纯读。

**⑥ `GET /storyboards/{id}`** — 详情，附加 `cliCommand`（实际将执行的 `dreamina-canvas` 命令回显，参数转义后拼接）与 `logs[]`（TaskWorker 追加的 `{ level, msg, ts }`，取末 20 条）。

**⑦ `POST /storyboards`** — 单条新增（前端 `Api.createStoryboard` 预留，无 UI 入口）。字段缺省取 `settings.defaults`，`status='queued'`。

**⑧ `PATCH /storyboards/{id}`** — 可改字段 `prompt/durationSec/model/ratio/resolution/seed/motion/negativePrompt`。已完成分镜改时长 → `40900`（`canEditDuration=false`）。`durationSec` 服务端 clamp 到 `meta.duration` 边界。⚠ 前端对步进器做了 300ms 合并，后端仍需支持高频 PATCH 幂等（同值重复 PATCH 直接返回成功）。

**⑨ `POST /storyboards/batch-duration`** — 逐条裁决，返回 `{ updated:[], skipped:[{id, reason:'completed_locked'|'not_found', message}] }`（部分成功不是错误，`code=0`）。

**⑩ `POST /storyboards/{id}/cancel`** — `succeeded` → `40900`；`queued`（未派发）→ 置 `canceled`；`generating` → 本地置 `canceled` 并放弃观察（见 §7.6 限制说明，message 中如实提示「任务已在即梦侧受理，取消仅停止本地跟踪」）。

**⑪ `POST /storyboards/{id}/retry`** — `failed`/`canceled` → 回 `queued`，`retryCount++`，清除错误字段，`resetProgress:true` 生效。后续由 worker 按恢复协议处理（已有 submitId 的复用，见 §7.4）。

**⑫ `POST /storyboards/batch-delete`** — 存在 `generating/queued` 且无 `force` → `40900` + `data.ids[]`；`force:true` → 删除并重排 `seq`。已派发任务同时清理 job state（不触达 CLI 侧）。

**⑬ `POST /storyboards/{id}/reorder`** — `{ direction:'up'|'down' }`，交换相邻 `seq`，返回受影响映射。

### 6.3 素材

**⑭ `GET /assets?projectId&type&keyword&inShotId`** — 返回 `{ currentShot[], library[], counts{currentShot,library} }`；每项带 `inCurrentShot` 标记（前端面板对勾依赖）。

**⑮ `POST /storyboards/{id}/assets`** — `{ assetId, role }`。单值 role（scene/prop/firstFrame/storyboard）覆盖旧值，`character` 可多个。绑定 `firstFrame`/`storyboard` 时复用已绑场景素材或独立素材均可，语义同 mock。

**⑯ `DELETE /storyboards/{id}/assets/{assetId}`** — 解绑。

**⑰ `POST /assets/upload`**（预留）— multipart 上传：落盘 `data/projects/{projectId}/assets/` → 入素材库。可选扩展：调 CLI `resource` 命令组导入即梦资源库并缓存 `cli_resource_id`（⚠ 具体 flag 以 `resource --help` 实测为准）。前端无 UI 调用，此接口本期可返回 `50000 未开启`（与 mock 行为一致），不影响其余功能。

### 6.4 批量提交（核心）

**⑱ `POST /storyboards/batch-submit`** — `{ ids[], concurrency? }`：

1. 前置检查：`settings.adapter.mode === 'cli'` 且 `!cliAvailable` → **整单拒绝 `51001`**（与 mock 行为一致：CLI 不可用时禁止提交）。
2. 逐条裁决，返回 `{ accepted:[{id, remoteId, status:'queued'}], rejected:[{id, code, message}] }`。拒绝场景：已在队列（`40900`）、积分类失败未清除（`51002`）。
3. `accepted` 项置 `queued`、清错误字段、`remoteId=null`；`concurrency` 参数后端二次裁决（clamp 1–5）并更新 `settings.queue.concurrency`（契约 8.4）。
4. QueueScheduler 唤醒，按并发闸逐件派发给 TaskWorker。

**⑲ `POST /storyboards/import/preview`** — `{ rawText, delimiter, trimEmpty, dedupe }` → `{ total, delimiterEcho, segments[{index,text,charCount,duplicate,tooLong}], warnings[] }`。拆分算法与前端 `splitSegments()` **逐字一致**：newline 类型按 `\r?\n`；custom 类型按 `delimiter.value` 字面拆分；每段 `trim()`、丢空段。`tooLong` 阈值 2000 字；`duplicate` 与现有 `prompt` 精确比对。

**⑳ `POST /storyboards/import`** — `{ rawText, delimiter, defaults?, batchId?, insertPosition }` + `Idempotency-Key`。同算法拆分后逐条建行（默认值合并 `settings.defaults`），`insertPosition:'top'` 时 `seq` 整体后移；返回 `{ created[], createdCount, batchId, skipped[] }`。重复策略按契约 8.3 默认**照建**（预览只标注）。

### 6.5 设置

**㉑ `GET /settings`** — 返回完整 Settings（3.4 结构）。`adapter` 段的 `cliAvailable/cliVersion` 由探测覆盖，客户端传入的值被忽略（只读）。

**㉒ `PUT /settings`** — 全量提交。校验：`queue.concurrency ∈ [1,5]`、`delimiter.type='custom'` 时 `value` 非空，失败返回 `40001 + data.fields[{path,message}]`（前端行内红字依赖此结构）。成功后若 `adapter.mode` 或 `queue` 变化，即时生效（并发闸重算；CLI 模式不可用时新任务只入队不执行）。

**㉓ `POST /settings/reset`** — `{ scopes:['delimiter','defaults','queue'] }` 按 scope 重置，返回重置后 Settings。

## 7. 后端调用即梦 CLI 的流程

### 7.1 CLI 事实基础（来自官方指南，全部确定）

```bash
dreamina-canvas --format json --non-interactive --region cn <group> <command> [flags]
```

- 命令组：`auth / canvas / model / node / operation / resource / schema / version / voice / completion`；全局参数：`--format json|table`、`--non-interactive`、`--profile`、`--region cn`、`--yes`。
- **开工四查**：`version`（版本）→ `auth status`（登录态）→ `model list --type video`（模型与可填 flags）→ 需要音色时 `voice list`。
- **生成链路**（视频）：`node create video --run` 一次完成「保存 → 报价 → 批准 → 运行」；批准方式用 `--credit-ceiling <n>`（报价 ≤ n 才继续，服务端强制）或 `--credit-token`（分步 `node quote → node confirm --credit-ceiling <n> → node run` 的产物）。也可省略 `--run` 只保存节点。
- **报价确认停点**：非 TTY 且未给批准方式 → 退出码 **10**，节点已保存、未扣费；失败信封含 `error.code=cli.generation_confirmation_required`、`creditConfirmation.minimumCreditCeiling`、`partialData.items[].nodeId/submitId`。
- **观察与恢复**：`node run` 返回的 `data.items[].submitId` 就是 `operation status|wait <submitId> --project-id <projectId>` 的 operation-ref。等待预算耗尽退出码 **20**（`operation_incomplete`，`requiredAction=resume`）——服务端任务可能仍在跑，**必须用原 submitId 继续观察，绝不能换新 submitId 重跑**（重跑 = 第二次运行 = 重复扣费）。
- **批量规则**：批量 `node run` 逐项显式 `--submit-id`（等长、同序、合法 UUID、先落盘后发请求）。
- **素材引用**：`--ref node:<node-id>` 引用画布节点；prompt 中 `{{node:<node-id>}}` 定位；引用优先 Node ID。视频 mode 由被引用素材的真实类型决定。
- **完成判定**：受理 ≠ 完成；必须看到**资源终态**与**选中的 Resource ID** 才算交付。
- **错误分类**：只按结构化字段（`error.code/class/retryable/requiredAction`）与退出码分支，不解析本地化 message；保留 `meta.requestId` 进日志。会员闸门样例：`service.10000 / access_denied / vip_membership_required`（策略拒绝，重试无用）。

### 7.3 TaskWorker 状态机（单个分镜的生命周期）

```
取件(queued, 并发闸内)
  1. 确保画布：项目级 canvas 复用（canvasId 存 job state）；
     无画布则 canvas create 一次（⚠ 具体参数以 canvas --help 为准）
  2. 确保引用：遍历 assets(role ∈ character/scene/prop/firstFrame)，
     assets.cli_node_id 有缓存 → 直接 --ref node:<id>；
     无缓存 → 经 resource 导入/上传得到节点后回填缓存
  3. 组装生成参数：prompt + refs + model(canonical) +
     时长/画幅/分辨率/运动强度 → 映射为该模型 modes[].flags 里实际存在的 flag
     （⚠ flag 名以 model list 实时返回为准，禁止硬编码未验证 flag）
  4. 预生成 submitId(UUID) → 写 cli_jobs（落盘先于 spawn，§7.4）
  5. spawn: node create video --run --credit-ceiling <ceil> --wait
            --timeout <观察预算>   （ceil = settings 的单任务积分上限）
  6. 分支：
     ok      → 校验资源终态 + selectedResourceId → 下载视频/封面到
               data/projects/{项目}/output/{分镜}/ → 更新行(succeeded, progress=100,
               videoUrl=/files/{项目}/{分镜}/video.mp4, coverUrl, elapsedMs)
     exit 10 → 报价超 ceiling：failed + 51002 语义（message 带最低报价
               minimumCreditCeiling）；若低于配置上限则按 partialData 的
               nodeId+submitId 补批准重跑（复用身份，不二次扣费）
     exit 20 → 用原 submitId 发 operation wait 续观（退避），超预算次数
               前不判失败；确证失败才 → 51004/51005
     error   → 按 §8 映射表归类（策略拒绝不重试）
  7. 收尾：置终态、dirty=1、写 logs[]；autoRetry 开启且错误可重试
     且 retryCount < maxRetry → 自动回 queued
```

**进度合成**：CLI 无细粒度进度。TaskWorker 按阶段写入 `progress`：受理 10 → 运行中按时间线性爬坡至 90 → 终态 100；`etaSeconds` 用该任务历史/全局平均耗时估算。前端已有 350ms 过渡平滑，跳变不敏感。

### 7.4 幂等与恢复（对应 CLI 硬纪律）

| 场景 | 后端动作 |
|---|---|
| 提交前崩溃 | submitId 已落盘但未 spawn → 重启后重跑同一 submitId，安全 |
| spawn 后响应丢失 | 不重放 run；用原 submitId 做 `operation status` 只读确认，再决定继续观察或按信封恢复 |
| `operation wait` 退出 20 | `requiredAction=resume` → 继续用原 submitId 观察（可跨进程、跨重启） |
| submission 状态 `absent` | 不可据此断定没跑过；先核对画布节点与积分账本再决策，绝不自动重提 |
| item 终态 `rejected` | 修正输入才有意义：置 failed + `51003`（策略/审核类），盲目重试无效 |
| 批量运行 | 沿用单件模型（每分镜独立 worker + 独立 submitId），天然满足「逐项身份落盘」要求 |

### 7.6 能力边界（如实声明）

| 项 | 说明 |
|---|---|
| 取消运行中任务 | CLI 公开命令组中**没有取消命令**。`cancel` 对 `generating` 只能停止本地跟踪并标记 `canceled`，即梦侧任务会继续跑完、积分照常消耗。行内取消按钮的语义在 message 中如实提示 |
| 细粒度进度 | CLI 不提供百分比进度，`progress` 为后端合成值（阶段 + 时间爬坡），`etaSeconds` 为估算 |
| 积分余额 | CLI 无余额查询命令，`/auth/me` 的 `credits` 返回 null |
| 会员闸门 | 非 VIP 账号下画布类操作被服务端拒绝（`vip_membership_required`），模型发现不受影响——meta/options 仍可用，提交会得到明确的 `disabledReason` 或失败信息 |

## 8. 错误处理机制

### 8.1 CLI 侧 → 业务错误码映射

| 观测 | 分类 | 业务 code | 前端表现（契约） |
|---|---|---|---|
| spawn ENOENT / version 或 auth 探测失败 / `loggedIn:false` | cli_down | `51001` | 顶栏适配器变红；batch-submit 整单拒绝 |
| exit 10（报价超 ceiling / 需确认且不可补批） | credit | `51002` | 行置失败 +「重试」 |
| item 终态 `rejected`（策略/审核） | policy | `51003` | 提示改写提示词，**不自动重试** |
| 观察超预算且确证上游超时 | timeout | `51004` | 自动重试（若开启），超次数置失败 |
| 提交身份丢失/进程中断且恢复失败 | interrupted | `51005` | 可重试 |
| 参数被 CLI 拒（提交前校验失败） | param | `40001` | 表单行内红字 |
| 其余 CLI 结构化错误（`error.code`） | internal | `50000` | Toast；`meta.requestId` 进 traceId 字段便于排查 |
| `error.class = access_denied`（实测：非会员账号调 `model list` 被闸门拒绝，`service.10000`） | permission | `40300` | 行内红条展示服务端原因；**策略拒绝不重试** |

### 8.2 重试与退避

- **TaskWorker 级**：`settings.queue.autoRetry=true` 且错误可重试（51004/51005/可重试传输错误）时，`retryCount < maxRetry(2)` 内自动回 `queued`；恢复一律复用原 submitId。
- **HTTP 级**：轮询接口恒 200 + 信封（无变化 `data:[]`），不制造 4xx/5xx 噪声；限流码 `42900` 预留给未来多客户端场景。
- **停止重试的硬线**：策略拒绝（51003）、会员闸门（access_denied）、积分不足（51002）——与 CLI「换 retry ID 没有用」的纪律一致。

### 8.3 幂等

- `Idempotency-Key`：`batch-submit` / `import` 落 `idempotency` 表，24h 内重放返回首次响应体。
- `PATCH` 同值幂等；`reorder` 以服务端 seq 为准，前端不做位置乐观更新（契约 9.2）。

## 10. 安全与运维

- **凭据**：CLI 登录态由其自身管理（OAuth，`auth login`）；后端不接触、不存储、不日志化任何 token/credit token/signed URL。
- **job state 原子写**：写临时文件后 rename；文件权限限当前用户。
- **日志**：CLI stdout 结构化 JSON 全量落 `data/logs/cli-*.log`（含 `meta.requestId`）；业务日志落标准输出。
- **限流面**：本地服务只绑 `127.0.0.1`；如需局域网访问，必须加 token 校验与 CORS 白名单。
- **积分配额**：单任务 `--credit-ceiling` 来自配置（建议默认取 `settings.queue` 之外的本地配置文件，前端 Settings 不感知）；批量提交前可选汇总报价，超出日预算时拒绝并提示。
